# forcediagnostics.ai

AI repair diagnosis for powersports service departments: fault codes, photos, video and tech notes in; a ranked diagnosis, parts and labor estimate, and after-action report out.

Live at [forcediagnostics.ai](https://forcediagnostics.ai).

## Stack

- [Next.js](https://nextjs.org) (App Router) + TypeScript
- Tailwind CSS
- Neon Postgres + Drizzle ORM
- Better Auth for sign-in
- Cloudflare R2 for manual PDFs
- Claude (Anthropic's API, `@anthropic-ai/sdk`) for Diagnose
- Hosted on Vercel

## Development

```bash
npm install
npm run dev
```

Copy `.env.example` to `.env.local` and fill it in first. Open [http://localhost:3000](http://localhost:3000). The home page is the sign-in screen (`src/app/page.tsx`); its animated topo background lives in `src/components/topo/`.

Before pushing, run:

```bash
npm run lint
npm test     # needs DATABASE_URL pointing at a disposable Postgres database
npm run build
```

CI (`.github/workflows/ci.yml`) runs the same checks on every push.

## Deployment

Vercel deploys automatically:

- Push to `main` → production (forcediagnostics.ai)
- Push to any other branch → preview deployment with its own URL

Build features on a branch, check the preview, then merge into `main`. Each Vercel build runs `npm run db:migrate` first (see `vercel.json`).

## Database

Postgres on [Neon](https://neon.com) in AWS US East 2 (Ohio), connected through Vercel's Neon integration. The integration sets `DATABASE_URL` for Production and Preview, and each preview deployment gets its own Neon branch, so test links never touch production data.

- Queries go through [Drizzle ORM](https://orm.drizzle.team) over `pg` (`src/db/`), the TCP connection pool Neon recommends for Vercel Fluid compute.
- Functions run in Vercel's `cle1` region (Cleveland, the same AWS region as the database), set in `vercel.json`.
- `GET /api/health` reports whether the app can reach the database.

### Schema changes

Edit `src/db/schema.ts`, then run `npm run db:generate` to write a migration into `drizzle/`. Commit it; the next deploy applies it.

### Keeping shops apart

Every shop-owned table has a `shop_id` and a Postgres row-level security policy. Shop-specific code runs inside `withShop(shopId, tx => …)` (`src/db/index.ts`), which switches to the `app_user` role and sets the shop for that transaction, so the database only returns and accepts that shop's rows even if a query forgets a filter. `systemDb` bypasses this and is only for sign-in and setup. `tests/shop-isolation.test.ts` tries to reach across shops and must keep passing.

When you add a table: give it `shop_id`, add a `pgPolicy` for `appUser` like the existing ones, and grant `app_user` access in a migration.

## Signed-in app

After sign-in staff land on the **Home** tab (`src/app/(app)/home`): a greeting by the time of day on the viewer's clock (the server render says "Welcome back" and the browser fills in the rest), then quick actions sized for a bay tablet: **New diagnosis** and **Continue** (the person's most recently used open diagnosis) for those who can diagnose, and a **Search the manuals** box that opens the Library's own search (`/library?q=…`; empty, it lists every manual, as does **Browse all manuals**). Below that, **Your open diagnoses** (the four most recently used that aren't solved and that the person started or sent a message in, with **All diagnoses**), and for managers and admins a strip linking to Diagnose: open diagnoses used in the last 7 days (only confirming a cause solves one, so one that ended another way stays open for good), started this month, and solved this month by when the fix was confirmed; no cost anywhere. A quiet line at the foot links to **Your account** and, for those who have it, **System Admin**. Account settings live on **Your account** (`src/app/(app)/account`), reached from the person's name in the header (beside Sign out) and from Home rather than a tab: the account's details, **Change password**, and the PIN for bay tablets (`setOwnPin` / `removeOwnPin` in `account/actions.ts`, both needing the password); in a PIN session on a bay tablet it says to change those from a computer or a phone instead. Techs, managers and admins get **Diagnose**, a chat with Claude about the unit in the bay (see Diagnose below). Everyone gets the **Library** tab, which searches the shop's manuals (see Manual library below). Admins, managers, service writers and parts staff also get **System Admin** (`src/app/(app)/admin`), showing only the sections their role allows; it opens on the first of them:

- **Customers** (service writers, managers and admins): the shop's customers, their contact details, the vehicles they've bought and sold, and each vehicle's diagnoses. See Customers below.
- **Sticker & Plate log** (service writers, managers and admins): each registration sticker the shop hands out, the customer it went to and the plate's classification. See Sticker & Plate log below.
- **Supplier** (parts staff, managers and admins): the shop's suppliers, as its dealer or accounting system lists them. See Supplier below.
- **Accounts** (admins): add staff (no email needed), change names and roles, reset passwords and PINs, disable and re-enable accounts. Admins can't change their own role or disable themselves, and the shop always keeps at least one active admin. Every change is written to the `audit_log` table and shown under Recent account changes.
- **Bay tablets** (managers and admins): pair and remove shared tablets, unlock locked PINs. See below.
- **Manuals** (admins): add the shop's PDF manuals to the library. See below.
- **Activity log** (managers and admins): everything changed in the shop, who did it and when, which nobody can edit or delete. See Activity log below.
- **Permissions** (admins): what each role can do. The table is `src/lib/permissions.ts`; server code checks it with `allows()` / `requireCapability()`, so the page and the rules can't drift apart. Managing accounts, tablets, settings and customers, deleting a diagnosis and reading the Activity log also need a password sign-in, never a PIN one.

## Sign-in

Staff sign in with company code, username and password through [Better Auth](https://better-auth.com) (`src/lib/auth.ts`); accounts, sessions and password hashes live in the Neon database. Usernames only have to be unique within a shop: they are stored as `<company code>.<username>`. There is no public sign-up.

The first shop and its admin are created once at `/setup`, which needs the one-time setup code and stops working as soon as a shop exists.

`BETTER_AUTH_SECRET` must be set in Vercel (Production and Preview). Changing it signs everyone out.

Wrong passwords are limited to 10 per account per 15 minutes, counted in the app's own `attempt_counters` table (`src/lib/attempts.ts`), on top of Better Auth's per-address limits.

## Bay tablets

Shared tablets in the bays sign people in with a 4–6 digit PIN instead of a password (`src/lib/bay.ts`, `src/lib/pins.ts`, `src/lib/bay-pin-plugin.ts`).

- **Pairing:** a manager adds the tablet under System Admin → Bay tablets on their own computer or phone, which shows a one-time code (8 characters, 10 minutes). Typing it at `/bay` on the tablet gives the tablet a random token in an HttpOnly cookie; the database only stores its SHA-256. Removing the tablet, or pairing it again, signs out everyone on it.
- **PINs:** staff set their own on Your account (needs their password), or an admin sets one on their page under Accounts. Easy PINs (`1234`, `2580`, years, repeats) are refused (`src/lib/pin-rules.ts`). PINs are hashed like passwords and the `app_user` role can't read the hashes.
- **Signing in:** `/bay` shows the shop's people who have a PIN; pick a name, type the PIN. Tablets only take PINs, never passwords, and a PIN only works on a paired tablet.
- **Lockouts:** 5 wrong PINs in a row lock that PIN for 15 minutes; 10 in a day lock it until a manager or admin unlocks it, a new PIN is set, or the person signs in with their password. A tablet pauses PIN sign-in after 15 wrong PINs in 15 minutes across everyone. After a right PIN, people are told about wrong tries on their PIN since they last used it, apart from their own typos just before.
- **Sessions:** a PIN session is tied to its tablet, lasts at most 12 hours, and ends on the server after 6 minutes without use. After 5 idle minutes the screen locks and ends that session, even across a reload; they type their PIN to carry on where they were, or anyone else taps Not you? to switch. Other tabs on the tablet follow whoever signs in or out. PIN sessions can't change passwords or PINs (Your account shows a note instead) or open any System Admin page (accounts, tablets and settings need a password sign-in).

## Customers

System Admin → **Customers** (`src/app/(app)/admin/customers`, `src/lib/customers.ts`, rules in `src/lib/customer-rules.ts`) is the shop's list of customers: everyone it sells to, buys from or services. It's for `repair_orders.intake` (service writers, managers and admins), signed in with a password: contact details stay off the shared bay tablets.

- **The list:** A to Z, 20 to a page, with each customer's phone, email and town and how many vehicles they've bought, sold to the shop or bring in for service. The search box works like the Diagnose list's (every word somewhere, any order and case; in the address as `?q=`), over the name, phone (also as bare digits, so `8145550199` finds "(814) 555-0199"), email, address and their vehicles' year, make, model, model number, VIN and color.
- **A customer:** name (the only thing needed), phone, email, street address, a second line, city, state and ZIP, and notes. Phone numbers are tidied as typed: ten digits, or eleven starting with 1, become "(555) 123-4567" (an extension stays as "x12"); a number with a + and another country's code, or a short local one, stays as typed. A two-letter state and postcodes are upper-cased. The page shows how to reach them (phone and email as links), then their vehicles, the details to edit, and **Remove customer**.
- **Vehicles:** each is **Bought from us** (with the date bought), **Sold to us** (sold or traded in, with the date) or **Theirs, for service** (bought elsewhere). Year, make, model, model number (upper-cased, as on the frame) and VIN (a whole one, checked like Diagnose's: never I, O or Q; a wrong check digit is kept and flagged on the vehicle's page) and color, and notes; the model, model number or VIN is enough. The ones they have come first, the newest deal first, and the ones they sold after. The same VIN can be on two records (traded in by one customer, bought by the next) and each vehicle's page lists the others.
- **Diagnoses and fixes:** under each vehicle, every diagnosis of it, newest first, with who started it, Open or Solved, and the fix: the cause the tech confirmed with **This was it**. Those who can use Diagnose open each from there, and **Start a diagnosis** on a vehicle opens New diagnosis with it picked (`/diagnose/new?vehicle=<id>`).
- **In Diagnose:** New diagnosis has an optional **Customer's vehicle** box over the quick form, which finds vehicles by the customer's name or phone, or the vehicle's model, model number or VIN (`searchCustomerVehicles`), showing only whose a vehicle is and what it is, never how to reach them. Picking one fills in its model number and VIN (or, with no model number, its year and model as the Model: "2021 Sportsman 850"), which the tech can still change; the diagnosis is tied to the vehicle (`diagnosis_conversations.customer_vehicle_id`). A diagnosis says whose it is under its title ("For Dana Whitfield · 2021 Polaris Sportsman 850", the name a link to their record for those who can open Customers), with **Change** and **Unlink**, or **Link a customer** for one started without; linking changes nothing Claude is told, and the unit stays as it is. A diagnosis carried on from a full one keeps its customer. Techs can pick and link vehicles (`diagnostics.work`, PIN sessions too) but can't open Customers.
- **Importing a list** (**Import** on the list, `src/app/(app)/admin/customers/import`, rules in `src/lib/customer-import-rules.ts`): customers and their vehicles from a CSV or Excel file (.xlsx or .xlsm, up to 20 MB and 50,000 rows), such as an export from a dealer system or a list kept by hand; **Download a template** gives a CSV with the headings it knows best. The file is read in the admin's browser, and nothing is saved until **Import** is pressed.
  - **Reading:** CSV as UTF-8, or UTF-16 when its byte order mark says so (Excel's "Unicode Text"), or else as Excel writes plain "CSV": Windows-1252 from Excel for Windows, Mac Roman from Excel for Mac, told apart by where the accented letters fall (in Mac Roman they're the bytes that Windows-1252 uses for punctuation, so they sit inside words), so accented names come out right; with commas, or semicolons or tabs when the first line has more of those. Excel workbooks are read by `src/lib/xlsx.ts`, written for this with no library (an .xlsx is a zip of XML; the browser unzips it): every visible sheet, picked from a list when there are several; numbers as Excel shows them; date cells as dates; ZIP codes in Excel's Zip Code format with their zero. A damaged workbook (its checksums don't match), or one shaped to be slow or to unpack to far more than its size, is refused rather than read. An old .xls, a password-protected workbook, .xlsb, .ods or Numbers file is refused with a note to save it as .xlsx or CSV.
  - **Columns:** the headings row is found among the first ten (a title line or two above it is fine); a list whose first row is already a customer (digits or an @ in it, and no heading the import knows) has none, and **No headings row** can be picked by hand. Each column is matched to a field by its heading as dealer systems and spreadsheets name them ("Customer Name", "First Name" and "Last Name", "Cell Phone", "E-mail Address", "Zip", "Model #", "Serial Number", "VIN/Serial #", "Unit VIN", "Delivery Date", "Deal Type"…); a loose name heading ("Customer", "Contact", "Owner") gives way to First and Last Name columns. The page lists every column with two examples from it and where it goes, any of which can be changed or left out; a name (or first and last names) is needed. Changing one column never changes another: two columns given the same field are flagged, and the first is read. A vehicle's columns also say which of the row's units they're for, Unit 1 to 10 (`readHeading`): a customer's units side by side in one row ("Unit 2 Model", "Vehicle 2 VIN", "2nd Unit Year", "Second Vehicle Make", "Model 2", "VIN #2") are read as their second unit and so on, each with its own deal type and date if it has those columns. Phone and email columns are choices instead, 1st, 2nd and so on (a mobile number first, then a plain "Phone", then home and work; "Phone 2" after "Phone"): each row's customer gets the first choice that has one, and the row's other numbers go in their notes ("Work Phone: (814) 555-0777"), so a customer with only a home number keeps it. "Address 2" stays the second address line.
  - **Rows:** each row is checked as the forms check them, but one bad value doesn't lose the customer: a phone number that isn't one ("call his wife"), an email without a domain, a VIN with a character missing or a date that isn't one is left out, with a note by row; a cell with two numbers or emails keeps the first. A ZIP code Excel stored as a number gets its leading zeros back ("2134" → "02134", and a ZIP+4's dash). Dates are month first ("6/24/2024", "6/24/24"), with the month's name ("24-Jun-24", "Jun 24, 2024") or as Excel stores them, with or without a time after them as dealer systems export them ("6/24/2024 12:00:00 AM", "2024-03-05 00:00:00.000"). Deal types read as Bought ("Bought", "New", "Used", "Purchase"), Sold to us ("Sold to us", "Trade-in") or Theirs, for service ("Service", "Owned"); a bare "Sold" could mean either way and isn't read as either, and a vehicle that doesn't say is the type picked on the page. A row with no name is left out; a row with vehicle details and nothing about a customer is another vehicle of the customer above it, as some dealer systems list them. A report printed to CSV repeats its headings after each page break and adds lines such as "Page 1 of 2", "Total units sold: 3" and "End of Report": those are left out, with a note.
  - **One customer, several units:** a customer's units can be on rows of their own, one per unit, with the customer's phone number on every row or only the first; on rows under the customer's with nothing about a customer; or side by side in one row. Rows with the same name are one customer unless something tells them apart (`sameCustomer`; names compared without case or extra spaces, phone numbers by their digits, any of a row's numbers counting): two different phone numbers (or emails) say they're two, even with an email in common (a family's), and a number on only one of them says nothing. Who a row is goes by what the row itself says, not by details earlier rows filled in, so the order of the rows doesn't decide it (`matchCustomer`): a row that shares a phone number or email with a customer is theirs; a row with only a name that two customers in the file could be goes with the one just above it if it's one of them, and otherwise is added as another customer with a note, never guessed. Each row's notes are kept, once. Two of the same model without a VIN are two units when their dates or colors differ. The preview shows how many customers and vehicles that comes to, the first few, and how many rows need a look and why, which downloads as a CSV (with a byte order mark, so Excel shows accents right).
  - **Saving** (`importCustomers` in `src/lib/customers.ts`): batches of up to 250 customers and 1,000 units (well under the 1 MB Server Action limit), one after another, with a progress bar; a customer with more than 100 units is sent in parts, each matched to the same customer. The tab warns before closing mid-import, and a big file's preview catches up after a column changes rather than holding the page. The server checks every customer and vehicle again. A customer already on file (matched the same way, so a file that leaves out the phone number still adds units to the right customer; names lower-cased by Postgres on both sides, so capitals in any language are found; the oldest first, so the same file always finds the same customer) isn't added again: their blank details are filled in from the file, each only if it's still blank as it's saved, so an edit made meanwhile stays, and nothing they have is changed. A name that several customers on file share, with nothing in the file to tell which, is added as another customer, with a note in the report. A vehicle they already have on record (the same VIN, or with no VIN, the same deal, year, make, model and model number and no differing date or color) isn't added twice. So importing a file again adds nothing new. An import that stops part way (the connection dropped) says so with **Carry on**, which sends the rest with the columns as they were set; choosing the same file again also keeps them. One import runs at a time per shop (a lock to the end of each batch), so two at once can't add the same customer twice. Each batch is recorded in `audit_log` as `customers.imported`, with the file name and counts, never customers' details. The end says (and moves focus to) how many customers were added, already on file (and filled in), how many vehicles were added or already on record, and what was left out. `tests/customer-import.test.ts` covers reading, matching columns, the rows' checks and grouping, and saving; `tests/xlsx.test.ts` the workbook reader.
- **Removing:** a customer or vehicle added by mistake can be removed (a customer's vehicles go with them), unless a diagnosis is tied to it: diagnoses are the shop's records, so the record stays (its foreign key stops it too). Unlink the diagnosis first if the link was the mistake (or a manager or admin deletes the diagnosis, if that was the mistake); a vehicle they've sold the shop is changed to Sold to us instead.
- **Records:** `customers` and `customer_vehicles` have a `shop_id` and row-level security like every shop table; a vehicle's composite foreign key keeps it with a customer of its own shop, and a diagnosis's with a vehicle of its own shop (`drizzle/0028_customers.sql`). `app_user` can add, change and remove them, but never move a customer to another shop or a vehicle to another customer (`drizzle/0029_customers_grants.sql`). Every change is written to `audit_log` (`customer.created`, `customer.updated`, `customer.removed`, `vehicle.added`, `vehicle.updated`, `vehicle.removed`): an edit records which fields changed, by name, never what they were or are. `tests/customers.test.ts` covers the rules, the shop isolation and the link to Diagnose.

## Sticker & Plate log

System Admin → **Sticker & Plate log** (`src/app/(app)/admin/sticker-plate-log`, `src/lib/sticker-log.ts`, rules in `src/lib/sticker-log-rules.ts`) logs each registration sticker the shop hands out: **Sticker #**, **Customer Name** and **Plate Classification**, 1 or 2. It's for `repair_orders.intake`, like Customers, signed in with a password.

- **Logging:** the sticker number (upper-cased, spaces evened out, a "#" or "No." in front dropped, so one sticker typed two ways is one: letters, digits, dashes, dots and slashes), the customer it went to, and the class. The customer box finds the shop's customers by name or phone number as it's typed (arrow keys and Enter, or a tap; their phone number and town tell two of a name apart), and offers to add the name typed as a new customer, who can be filled in on Customers later. After logging one, the form is ready for the next: the number and customer clear and the class stays. **Log a sticker** on a customer's record opens the form with them picked.
- **One sticker, once:** a sticker number is logged once per shop (a unique key on shop and number); logging it again says who it went to. Each shop has its own numbers.
- **The log:** newest first, 25 to a page, with when each was logged and by whom. **All**, **Class 1** and **Class 2** filter it, and the search box finds a sticker number or a customer's name or phone number (every word, any order; `?q=` and `?class=` in the address). **Download CSV** gives the log as searched and filtered, oldest first, with its dates in the viewer's time zone (`/admin/sticker-plate-log/export`), with a byte order mark for Excel and a cell starting with = + - or @ kept as text. Each customer's page lists their stickers.
- **Corrections:** an entry's number, class or customer can be corrected, or it can be removed if it was logged by mistake. Every entry, correction (which fields, and the old number) and removal is written to `audit_log` (`sticker.logged`, `sticker.updated`, `sticker.removed`).
- **Records:** `sticker_plate_log` has a `shop_id` and row-level security like every shop table; a composite foreign key keeps each entry with a customer of its own shop (`drizzle/0030_sticker_plate_log.sql`), and `app_user` can't move an entry to another shop (`drizzle/0031_sticker_plate_log_grants.sql`). A customer with stickers logged can't be removed: the log is the shop's record of them. `tests/sticker-log.test.ts` covers it.

## Supplier

System Admin → **Supplier** (`src/app/(app)/admin/suppliers`, `src/lib/suppliers.ts`, rules in `src/lib/supplier-rules.ts`) lists the shop's suppliers with the headings the shop's own systems use: **Supplier ID**, **Supplier Code**, **Supplier Name**, **Category Code** and **Category ID**. It's for `parts.manage` (parts staff, managers and admins), the capability that covers vendors; supplier details aren't personal, so a PIN sign-in on a bay tablet can open it too.

- **The list:** by Supplier ID (as numbers when they are, so 2 comes before 10), 25 to a page. The search box finds any of the five (every word, any order); a Category Code select narrows it (without case); both live in the address (`?q=`, `?category=`). **Download CSV** gives the list as searched and filtered, with its headings (`/admin/suppliers/export`), a byte order mark for Excel and a cell starting with = + - or @ kept as text.
- **A supplier:** a Supplier ID and a Supplier Name are needed; the codes and the category are optional. Supplier ID is the shop's own key: once per shop, matched without case ("v100" is "V100"). **Add supplier** suggests the next number when every Supplier ID is a number. A Category Code the shop already uses is offered as it's typed and fills in its usual Category ID. Suppliers can be corrected or removed; every change is written to `audit_log` (`supplier.created`, `supplier.updated` with the fields changed, `supplier.removed`).
- **Importing a list** (**Import**): a CSV or Excel file (read in the browser as Customers' import reads them), or rows pasted straight from a spreadsheet, headings and all. The headings row is found among the first ten, and each column is matched to a field by its heading (the five above, or a vendor list's "Vendor #", "Vendor Code", "Vendor Name", "Category", "Cat ID"), changeable on the page. One row per Supplier ID: a later row with the same ID is the one used, with a note; rows without an ID or a name are left out, with a note. The server checks every row again and matches suppliers on file by Supplier ID: one on file takes the file's details, but a blank cell leaves what's on file; one that isn't is added. So importing the same list again changes nothing, and an updated export brings in only what changed. Batches of up to 500, one import at a time per shop, each recorded in `audit_log` as `suppliers.imported` with its counts; a stopped import has **Carry on**.
- **Records:** `suppliers` has a `shop_id` and row-level security like every shop table, and a unique index on the shop and the lower-cased Supplier ID (`drizzle/0032_suppliers.sql`); `app_user` can't move a supplier to another shop (`drizzle/0033_suppliers_grants.sql`). `tests/suppliers.test.ts` covers it.

## Activity log

System Admin → **Activity log** (`src/app/(app)/admin/activity-log`, `src/lib/audit-log.ts`, words and CSV in `src/lib/audit-log-rules.ts`) is the shop's `audit_log` as a report: every change written to it (accounts and PINs, bay tablets, customers and their vehicles and imports, stickers, suppliers, manuals and the model list, deleted diagnoses), the newest first, 25 to a page, each with its number, what happened in words ("Changed Dana Whitfield's phone number", "Deleted the diagnosis “Misfires under load”" with its unit, who started it, how far it got and why it was deleted), who did it and when. It's for `audit.read` (managers and admins), signed in with a password.

- **Finding things:** **All** or one area (Diagnoses, Customers, Sticker & Plate log, Supplier, Accounts and PINs, Bay tablets, Manuals), and the search box (every word, any order, over who, the kind of entry and everything it says; `?q=` and `?area=` in the address). **Download CSV** gives the log as searched and filtered, the oldest first, with the times in the viewer's time zone: each entry in words and as stored, with its hash and the one before it (`/admin/activity-log/export`; a byte order mark for Excel, and a cell starting with = + - or @ kept as text).
- **Nobody can alter it.** There's nothing in the app to edit or delete an entry with, `app_user` can only read and add entries (`drizzle/0004_staff_admin_grants.sql`), and triggers refuse every change, delete and `TRUNCATE` for every role, the database's owner included (`drizzle/0035_audit_log_locked.sql`). An account that's in the log can't be deleted either (disable it instead), so no entry loses who it was by. An entry only goes when its whole shop is removed, which nothing in the app does.
- **Sealed, so tampering shows.** An owner could still turn the triggers off. So as the transaction that adds an entry commits, a trigger seals it (`audit_log_seal`, which runs as the owner): its number in the shop's log (`seq`, from 1, one shop at a time so they follow the order entries were saved in), the time, its author's name as it is then (`actor_name`, so a rename later doesn't rewrite history), and a SHA-256 hash (`audit_log_hash`) over all of that, what it says, and the hash of the entry before it (`prev_hash`). Whatever an insert puts in those columns is replaced. Entries already in the log were sealed in the order they were made when the migration ran.
- **The check:** each time the page is shown, the database works every entry's hash out again (`verifyAuditLog`) and the page says whether the log checks out, or where it stops: an entry changed after it was written (it no longer matches its hash), one taken out (a gap in the numbers), one changed and its hash worked out again (the entry after it was sealed after something else), or one slipped in without a seal. It also shows the latest entry's hash, its **fingerprint**, which stands for the whole log up to it: note it down, or keep the CSV, and a later look shows whether anything up to it has changed or gone, even if the whole chain was worked out again.
- A new kind of entry needs its words in `describeAuditEntry`; until then it shows as its action and record. `tests/activity-log.test.ts` covers what the log says and its CSV, that neither the app nor the owner can change, delete or empty it, the seals and the check finding each kind of tampering, and deleting a diagnosis.

## Manual library

The **Library** tab searches every page of the shop's service and owner manuals and opens them at the right page; admins add the PDFs under System Admin → **Manuals**. Manuals are licensed to the dealership, so each shop has its own library: `manuals`, `manual_pages` and `manual_file_names` have a `shop_id` and row-level security like every shop table, and a file added by two shops is stored twice.

- **Files** live in a private Cloudflare R2 bucket under `shops/<shop id>/manuals/<manual id>.pdf`, reached through R2's S3-compatible API with [aws4fetch](https://github.com/mhart/aws4fetch) (`src/lib/storage.ts`). Browsers upload and download straight to and from R2 with presigned URLs, handed out only after a permission check: uploads last an hour and must be sent as `application/pdf`, downloads last 15 minutes. Files never pass through Vercel, which takes at most about 4.5 MB per request. The R2 keys stay on the server.
- **Adding** (`src/app/(app)/admin/manuals/`, `src/lib/manuals.ts`): admins choose PDFs, a whole folder, or drag them in; anything that isn't a PDF is left out. For each file the browser works out its SHA-256 and checks [pdf.js](https://mozilla.github.io/pdf.js/) can open it, then asks the server what to do. A file already in the library is skipped, whatever it's called (see One manual, several names below). One that stopped part way carries on, without uploading again if the whole file already reached R2. Otherwise the browser uploads it, the server checks its size in R2, and the browser reads each page's text with pdf.js and sends it in batches, each well under the 1 MB Server Action limit. Once every page is saved the manual shows in the library and `audit_log` records it (`manual.added`). Pages with no text layer are counted and left for OCR (Scanned pages, below). Two files go at a time. Damaged or password-protected PDFs fail with a reason and a Retry button, and the rest carry on. If the connection drops, files wait and carry on when it's back. Choosing the same folder again retries what failed and leaves the rest alone, and if the tab closes, choosing it again finishes what's left.
- **Search** (`src/lib/library.ts`) is Postgres full-text search over `manual_pages`, one row per page with a stored `tsvector` column and a GIN index. Under row-level security Postgres can't use that index (the match operator isn't leakproof), so search finds pages through the `ready_manual_pages` view (`drizzle/0010_manual_search.sql`), which belongs to the table owner and makes the same shop check itself. It takes web-search syntax: plain words (all must match), `"quoted phrases"`, `or`, `-word`. Fault codes like `P0300` and part numbers like `2205123` match as whole words. Results are the 50 best pages, with the matches highlighted. Filters (below) apply after the index has found the matching pages, in a materialized CTE whose `WHERE` they stay out of: otherwise Postgres, guessing a filter leaves a manual or two, reads those manuals' pages one by one, which is slow when it matches hundreds. Only the pages a filter (or Diagnose's unit scope) keeps are ranked, though: ranking reads each page's whole `tsvector`, which is most of the time a common word takes, so the filters are a `CASE` in the CTE's select list and a page they leave out gets no rank. `tests/manuals.test.ts` checks the plan with and without filters.
- **Viewer** (`/library/<id>?page=N`): pdf.js draws one page at a time and reads only the parts of the PDF that page needs, with HTTP range requests, so a 100 MB manual opens on a bay tablet without downloading all of it. The viewer makes those requests itself (`src/app/(app)/library/[manualId]/storage-pdf.ts`) rather than leave them to pdf.js, which never asks again for a part whose request failed and leaves every page that needs it loading for good. When its link runs out it gets a new one and asks again; a part that can't be had (the connection dropped, or nothing arrived for 30 seconds) makes it open the file afresh, and failing that the page says it couldn't be shown, with Try again (`tests/manual-viewer.test.ts` checks the fetching, renewing and breaking with pdf.js and a stand-in for storage). A link to a manual (a search hit, the Library list, a Diagnose source) opens at its page even if that manual was left open at another one. The address follows the page being read, and Back or Forward to a visit shows the page in its address, where that visit was left, even when Next brings back another visit's viewer (the same link followed twice shares one) or makes the viewer again after dropping it. An admin can read a manual in the same tab while an upload runs: the Manuals list only refreshes while Manuals is on screen, rather than reload the page they're reading, and catches up when they go back. Scanned-page images (CCITT, JBIG2, JPEG 2000) need pdf.js's WebAssembly decoders, which `npm run dev` and `npm run build` copy into `public/pdfjs/wasm/` (`scripts/copy-pdfjs-wasm.mjs`). **Open full PDF** goes through `/library/<id>/file`, which hands out a fresh link each time.
- **Who can:** everyone can search and read (`library.read`), including PIN sessions on bay tablets. Adding manuals, the model list and reading scanned pages need `settings.manage`: admins, signed in with a password.

### Scanned pages (OCR)

Some manuals are scans: pictures of pages with no text layer, so search can't find anything on them (the 1985-1995 Vol. I service manual is 424 of them). The **Scanned pages** card on System Admin → Manuals reads the words on those pages with [Tesseract.js](https://github.com/naptha/tesseract.js) (OCR, English), in the admin's browser: the PDF comes straight from the shop's R2 bucket, nothing goes to an OCR service, and only the text reaches our server. It's free, and it's private to the shop.

- **What gets read** (`src/lib/manual-ocr.ts`): the pages of ready manuals that have nothing search can find and that OCR hasn't read yet (`manual_pages.ocr_at` is null): a page with no text layer, or only a stray mark or two (under 64 bytes). A partial index, `manual_pages_to_read`, holds just those pages, so finding them never reads the whole table, and building it only checked each page's length (`drizzle/0016_manual_ocr.sql`).
- **In the browser** (`src/app/(app)/admin/manuals/ocr-job.ts`, rules in `src/lib/manual-ocr-rules.ts`): **Read scanned pages** asks the server what's left, then for each manual pdf.js opens the PDF with range requests (only the scanned pages' parts are fetched; a new link every 10 minutes, since links last 15) and draws each page at 300 dpi, or less for pages over 12 million pixels (fold-outs), with pdf.js's print mode so it keeps going in a background tab. pdf.js's image decoders (CCITT and JBIG2, JPEG 2000) are fetched once per tab and handed to it by the job: when one doesn't load, pdf.js would draw the scan blank and OCR would save it as a page with no words, so instead the page is drawn again from a fresh copy of the PDF, and listed with Retry if that fails too. The page is turned grey (a PGM image, much quicker for Tesseract than PNG) and long, thin ruled lines are taken out: Tesseract reads a ruled torque table as a picture and gets little of it, and without the rules it reads the cells. Only lines with light paper either side count, so a dark grey photocopy or white words in a black panel are left as they are. A Tesseract scheduler reads pages with one worker per processor less one, from one to four. From Tesseract's word list (TSV, with a confidence for each word) it keeps the words it's sure of (50 and up; 20 for fault codes and part numbers, which aren't in its dictionary), drops lines that are mostly guesses (what it makes of photos and drawings) and fixes O-for-0 and l-for-1 in codes and part numbers ("PO300" → "P0300"). Text goes to the server ten pages at a time, well under the 1 MB Server Action limit.
- **On the server** the text is cleaned and capped like uploaded text, and only ever goes to a page that's still left to read: text from the PDF or an earlier OCR is never changed (a stray mark from the PDF stays, with OCR's words after it). Each page read gets `ocr_at`, even when OCR found no words (a blank page, a photo), so it isn't read again. A manual's `pages_without_text` and `pages_read_by_ocr` drop and rise as pages are read. Every batch that changes pages is recorded as `manual.ocr` in `audit_log`, with its page numbers, in the same transaction as the text (its words are in search straight away, whether or not the manual is ever finished); the batch that reads a manual's last page counts them again from the pages, and its row says `finished` with the counts (pages read, pages with text, pages still without). Search needs no change: the `tsvector` is generated from the text, so OCR's words are found, highlighted and open at their page like any others.
- **The card** shows how many manuals and pages are left and a rough time; while it reads, the manual and page, pages read, pages a minute and time left, with **Pause** and **Resume** (pausing waits for the pages being read, saves them and stops Tesseract to give its memory back). The tab warns before closing while it reads, not while paused, and holds a screen wake lock so the computer doesn't go to sleep while the tab is in front (browsers let go of it when the tab is hidden; for a long run, leave the tab in front or set the computer not to sleep). If the connection drops it waits and carries on: when a step fails, it asks the server (`/api/health`) whether it's there, since the browser still says it's online when only the shop's internet is down, and waits (checking again after 5 seconds, doubling to a minute) without counting it against the page. If the app is updated mid-run, it stops and says to reload the page. If three manuals, or twenty pages, fail one after another with the connection up and nothing saved in between (file storage down, say), it stops with a note rather than working down the whole list; a damaged or password-protected file, or one missing from storage, is only that manual's problem and doesn't count. A manual or page that can't be read (a file storage won't hand over, a page pdf.js can't draw, a page Tesseract fails on twice) is listed with **Retry**, stays unread, and the rest carry on. If the tab closes, pressing **Read scanned pages** again carries on with what the server says is left; at most the last few unsaved pages are read again. One tab reads at a time (the Web Locks API), and the run keeps going while the admin looks at another part of the app.
- **New uploads** don't run OCR (it's far slower than adding a file): the uploader says how many pages are scanned and points to the card. The admin list says how many pages OCR read ("12 pages read by OCR") and still flags pages without text, saying whether OCR hasn't read them yet or found no words on them (blank pages, pictures).
- **Files:** Tesseract's worker, its WebAssembly engine (the LSTM-only builds, with and without SIMD; it picks one) and the English data (`4.0.0_best_int`, 3 MB) are copied into `public/tesseract/` by `scripts/copy-tesseract.mjs` before `dev` and `build`, from the pinned `tesseract.js`, `tesseract.js-core` and `@tesseract.js-data/eng` packages. Nothing is loaded from a CDN. The browser keeps the English data after the first run.
- **Speed:** about a second a page or a little under with three workers on a 4-core computer (measured in headless Chromium at 300 dpi: 0.8 s a page through a 60-page scanned manual, 0.8–1.1 s on test pages; 2.3 s with one worker), so the 424-page Vol. I manual takes 6 to 8 minutes and 10,000 scanned pages 2 to 3 hours. More cores read faster, up to four workers; 200 dpi would be about a third quicker but reads small print (6–8 pt tables and notes) worse.

### Model list

Polaris's STOP site gives a spreadsheet of which models each manual covers. Saved as CSV (`manual-list - All.csv`) next to the PDFs, it tags every manual with its brand, model years and model numbers, so the Library can filter by them and Diagnose can read only the manuals for a unit's model number.

- **Adding it:** drop the folder with the PDFs and the CSV on System Admin → Manuals, or choose the CSV on its own with **Choose files**. Any `.csv` with the right header is imported first, before any PDF starts, and gets its own row: "Model list: 440 manuals, 18,203 models (52 brands filled in from model numbers)". A CSV with another header is reported and skipped. The **Model list** card shows how many manuals are added and listed, and (folded away) which manuals aren't in the list and which entries have no PDF yet.
- **Format**, exactly as the export script writes it: UTF-8 (a byte order mark is fine; a list Excel saved again as plain "CSV (Comma delimited)", which is Windows-1252, is skipped with a note to save it as "CSV UTF-8" instead, rather than turning ® into �), CRLF or LF line breaks, fields in double quotes (quotes inside doubled), and the header `"File","Brand","Article","Posted On","Title","Model Years","Year","Model Number","Model Description"`. One row per manual and model; a manual with no models has one row with Year, Model Number and Model Description blank. File is the PDF's file name, Brand Polaris's category code (`ATV`, `RGR`, `RZR`, `GEN`, …; see Vehicles below), Posted On `6/24/2024`, Year `2020`, Model Number `Z24NAE99AK`. Rows with a blank File (manuals with no download) are skipped. A row with the wrong number of columns stops that CSV; a manual with a bad date or a year outside 1950–2100 is left out, with the row number, and the rest go in.
- **How it's read** (`src/lib/csv.ts`, `src/lib/manual-catalog-rules.ts`): the browser parses the CSV (RFC 4180: quoted commas, quotes and line breaks), groups the rows by file and sends them in batches well under the 1 MB Server Action limit, never splitting one file's rows. The server checks every field again (`src/lib/manual-catalog.ts`). Model numbers are stored upper-cased and line breaks in fields become spaces.
- **Matching by file name:** the list is kept apart from the manuals, one entry per file in `manual_catalog_documents` and one row per model in `manual_catalog_models` (both shop-owned, with row-level security), keyed by the lower-cased file name. So it can be imported before or after the PDFs, in any order, and a manual uses the entry for each name it's known by (`manual_file_names`, below) whatever the case. File names are only trimmed, never otherwise tidied, on both sides, so a name with two spaces or a no-break space in it still matches. The Library and the admin list then call the manual by Polaris's subject line ("2027 RZR Pro R Boost / Pro R Boost 4") instead of its file name, with the brand and model years beside it. The PDFs have to keep the names the CSV lists. A browser's copy number counts as the same name: a manual added as `X (1).pdf` (the files downloaded a second time into the same folder) is also known as `X.pdf`, unless another manual already is (`withoutCopyNumber`; `drizzle/0015_manual_copy_numbers.sql` did the same for manuals added before). That name follows the same rules as any other (below): a ready manual takes it from one that never finished, and a ready manual that has it keeps it, which the uploader says when the newer download finishes, as it does for exactly the same name ("A different manual is already called X.pdf, so the model list goes with that one."). `drizzle/0020_manual_plain_names.sql` gave such names, where 0015 or the app before it had left them with a manual that never finished, to the ready manual (the first to be ready, if there were two). Only one or two digits count, so a name like `… (2415113).pdf` is left alone.
- **One manual, several names:** Polaris lists some PDFs more than once under different names: the Winch Diagnostic & Troubleshooting Guide is `9860049R01.pdf` and `9860049R01-2.pdf` … `-5.pdf` (entries under XXP, GRL and other brands), and the RZR 800 manual is both `9924882_2014_RGRRZR800.pdf` and `9924882_2014_RZR800.pdf`. The uploader stores each PDF once, so `manual_file_names` keeps every name a manual is known by, one row per name (`shop_id`, `manual_id`, `file_name`, and `file_key`, the lower-cased name). A name belongs to one manual at most (its key is `shop_id` + `file_key`), and a composite foreign key keeps it in its manual's shop; `app_user` can read and add names, never remove or rename one; it can only move one to another manual of the shop (below). A new manual records its own name in the same transaction. When a file turns out to be one already in the library under another name, `startManualUpload` links that name to the manual and the uploader says so ("Same file as 9860049R01.pdf, already in the library. Linked this name to it.", recorded in `audit_log` as `manual.name_linked`), uploading nothing; a name some other ready manual (a different file) already has stays with that one, and the uploader says so too. A name held by a manual that never finished (an upload that stopped and was never tried again) goes to the first ready manual that asks for it, when it finishes or when a copy of it is chosen under that name, with or without a copy number (`claimName`), so an abandoned row can't keep a newer download out of the model list. So choosing the whole folder again after an upload links every duplicate name, at one short server call per file. `drizzle/0014_manual_file_names_grants.sql` gave every manual added before this its own name (of two that share a name, whatever the case, a ready one keeps it over one that never finished, and otherwise the older one); the duplicates' names come from choosing the folder again.
- **A manual's entries:** with several names, a manual can have several entries. It's called by the title of the entry for its own file name, or failing that its first other listed name (A to Z), or failing both its file name. Its Model Years are its entries' Model Years, or when they differ, the earliest year in them to the latest (the RZR 800 manual's `2013` and `2014` make `2013-2014`), whichever name is its own. Brands are all its entries' brands, once each ("Ranger, RZR, General, Xpedition, ATV"), and the admin list counts each of their models once and shows its other names ("Also named …"). The Model list card counts a manual as "not in the model list" only when none of its names is listed, and an entry as "no PDF added yet" when no manual is known by its name. The SQL for these is in `src/lib/manual-catalog.ts` (small subqueries per manual, by index).
- **Importing again** replaces each listed file's entry and models in one transaction: the same CSV again changes nothing, and a newer CSV wins for the files it lists while the others keep their entries. With two CSVs (an older `manual-list - ATV.csv`, say), the older file by its date goes first, so the newer one has the last word, whether they're in one folder or added one after the other. Lists import one at a time, oldest first by date (then name), and PDFs wait for them. A list that goes in after a newer one added since the page was opened (the folder dropped after `manual-list - All.csv` was chosen on its own, a **Retry**, or the folder chosen again after a list failed) is followed by that newer list, imported again, so it can't put its older entries over the newer ones. Each import is recorded in `audit_log` (`manual_catalog.imported`, with counts).
- **Blank brands** (about 50 "web manuals") are filled in after each import, learned from the entries that do name theirs (`inferBrands`). Words in the title and model descriptions come first ("RANGER", "SPORTSMAN", "GENERATOR"): a word counts only when at least 90% of the named entries using it, and at least two of them, share a brand, and the top brand needs twice the runner-up's words. Failing that, model numbers vote by first letter, but only letters 95% of named entries agree on, since product lines share letters (in Polaris's list `P` covers generators and some ATVs, `R` Rangers and older RZRs); the top brand then needs two-thirds of the entry's model numbers. Anything unclear stays blank: on Polaris's full list this fills in 46 of the 53 blank entries, all correctly, and leaves 7. Filled-in brands show as "(filled in from its models)" on the admin list and are worked out again on every import.
- **Vehicles:** the app calls Polaris's codes by name, from a small table in `src/lib/manual-catalog-rules.ts`: `RGR` Ranger, `RZR` RZR, `GRL` General and `XXP` Xpedition are UTVs (side-by-sides), `ATV` is ATVs and `GEN` Generators. Any other code shows as it is, under Other. The labels show everywhere instead of codes: search results, the list of manuals, the viewer's header and the admin list ("Ranger · 2019-2022 · 17 models", or "Ranger (filled in from its models)").
- **Filters** on the Library: Vehicle, Year, and Model, which matches a model number or its start (`Z24NAE99`) or the start of words in model names or in the manual's title (`RZR XP 1000`). The title counts because Polaris's descriptions of older models often shorten the name it spells out, about one entry in ten on its full list: the `2009 SPORTSMAN XP 850 Service Manual`'s models are `SPM XP 850, PNTD RED` and so on, the `2008 RANGER 500 Service Manual`'s `2X4,500 CARB, EB GRN`, so `Sportsman XP 850` or `Ranger 500` finds them by their titles (`manual_catalog_documents.title_words`, built like `model_words`). The words all come from the model's own name or all from its entry's title, never some from each: a title that covers several sizes or lines (`2018-2019 RANGER 900 / 1000`) would otherwise lend a `RANGER XP 900 EPS` the other size's number, and `Ranger XP 1000` would get the 900's manual. In a title, numbers and words shorter than three letters only match whole words (`S` isn't `Service`), and years and the words most titles have (`Service`, `Manual`, `Wire`, `Diagrams`, `Chapter`, ...) don't match titles at all (`modelWordsMatch`). The make, `Polaris`, isn't a Model word at all (`modelFilterWords`), here or in Diagnose: every model in the list is a Polaris, and in Polaris's own descriptions the word is nearly always paint (`SPORTSMAN 570 - POLARIS PURSUIT CAMO`, `POLARIS BLUE`), so `Polaris Sportsman 570` would otherwise find only the camo models' manuals and miss the rest (on Polaris's full list, Year 2023 and `POLARIS SPORTSMAN 570` found 3 of the 77 models and 3 of their 5 manuals). Vehicle is one select: All vehicles; UTVs (side-by-sides) with the lines present indented under it (Ranger, RZR, General, Xpedition); ATVs; Generators; and Other with any other codes, each with how many ready manuals it has (a manual listed for a Ranger and a RZR counts once under UTVs). Filters narrow both search results and the list of manuals and live in the address so a filtered search can be shared: `?vehicle=UTV` (or `ATV`, `Generator`, `Other`) for a vehicle, `?brand=RGR` for one line (older `?brand=ATV` links still work), as in `/library?q=carburetor&vehicle=ATV&year=2020`. A manual with several entries shows when one of them matches every filter that's set (an entry with no brand counts as having the brands of the manual's other entries, so the RZR 800 manual, whose 2013 models are listed under a name with no brand, shows for RZR + 2013), and a year and model have to match the same model (or the model's entry, for words in its title: Year 2009 and `sportsman` find the 2009 Sportsman XP 850 manual, Year 2010 doesn't). Year goes by the models' Year column; an entry with no dated models (a manual listed without any) goes by its Model Years text instead (`2018-2027`, `2020, 2022`), and an entry listed without models matches Model by its title alone (not Year and Model together, which need a model of that year). Manuals that aren't in the model list only show without filters. Search still finds pages with the GIN index first and only then filters them (`tests/manuals.test.ts` checks the plan with vehicle filters too). The filters themselves are worked out once per page load, as arrays (the matching entries, then the manuals known by their names; for Model's words, the entries whose titles have them), never as subqueries or joins Postgres could run again for every page, entry or model: when it underestimates a shop's list, as it does until autovacuum has gathered statistics on a fresh import, those joins took seconds to minutes on a list the size of Polaris's. For Diagnose, `manualsForModel(shopId, modelNumber)` in `src/lib/library.ts` returns the ready manuals that list a model number exactly, under any of their names.

### Setting up R2

1. In the Cloudflare dashboard, open **R2 → Create bucket** and name it, for example `forcediagnostics-manuals`. Leave public access off: no public `r2.dev` URL and no custom domain.
2. In the bucket's **Settings → CORS policy**, add this policy so browsers can upload to it and read pages from it:

   ```json
   [
     {
       "AllowedOrigins": ["*"],
       "AllowedMethods": ["GET", "PUT", "HEAD"],
       "AllowedHeaders": ["Content-Type", "Range"],
       "ExposeHeaders": ["Content-Range", "Accept-Ranges", "Content-Length", "ETag"],
       "MaxAgeSeconds": 3600
     }
   ]
   ```

   Any origin is fine here: the bucket isn't public, and every request needs a presigned signature from the app, which is the access control. CORS only decides which websites' scripts may read the responses. To narrow it anyway, list `https://www.forcediagnostics.ai` and the preview URLs instead of `*`.
3. Open **R2 → Manage API tokens → Create API token**. Give it **Object Read & Write** permission, applied to that bucket only. Copy the Access Key ID and Secret Access Key; Cloudflare shows the secret once.
4. In Vercel → Settings → Environment Variables, add these for **Production** and **Preview**, then redeploy:
   - `R2_ACCOUNT_ID`: the Cloudflare account ID (on the R2 overview page)
   - `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`: from the token
   - `R2_BUCKET`: the bucket name

   Leave `R2_ENDPOINT` unset; it only points local tests at a stand-in server. Until the four are set, Manuals and the viewer say storage isn't set up, and search still works.

Do the full upload on production (www.forcediagnostics.ai). Each preview deployment has its own Neon branch, so manuals added on a preview vanish with it, while their files stay behind in the bucket. To try the uploader on a preview, use a few files, or give Preview its own `R2_BUCKET`.

### Limits

- OCR reads English, and printed text best: on test scans, 98% of all words, every part number, and most made-up fault codes (B for 8 and S for 5 are its usual slips). Tables are read cell by cell, a row to a line, without their columns lined up. Drawings and wiring diagrams give only their bigger labels, and photos and handwriting little or nothing. Pages scanned sideways read badly (it doesn't turn pages round), and fold-outs bigger than 12 million pixels at 300 dpi are read at a lower resolution. A scanned page whose PDF already has a little text on it (a page number a scanner stamped, say) counts as having text and isn't read.
- Manuals can't be deleted or renamed by hand yet, and a name linked to a manual can't be unlinked; the title comes from the model list, or else from the file name, without `.pdf` and a leading `001 - `-style number. A newer download saved under a name the library already has, exactly or with a browser's copy number, is added as a manual of its own, but the model list stays with the older one (the uploader says so), unless the older one never finished.
- Model-list entries can't be deleted from the app, only replaced by importing a corrected list. Lists are put in order by date only among those added since the page was opened, in one tab: a list added after reloading the page replaces the entries already in, whatever its date (which is also how to put an older list back), and two tabs importing lists at the same time take turns batch by batch, so a file both lists have keeps whichever batch came last (importing the newer list again puts it right). Brand filling goes by first letter only, so a letter two product lines share (if General and RZR model numbers both start with `Z`, say) can tip a web manual into the bigger one when that one has two-thirds of the entries.
- Up to 500 MB per file and 50,000 characters of text per page (the rest of a page is cut off).
- Search ranks every page a query matches, so a word on nearly every page (`polaris` from the footers, `service`, or only an excluded word like `-oil`) takes about a second over 100,000 pages: 0.5–1.4 s measured on a local Postgres, likely more on Neon. A filter or Diagnose's unit scope brings that down to a few hundred milliseconds, since only the pages it keeps are ranked, but the index still finds every matching page first. Codes, part numbers and phrases (`P0300`, `spark plug gap`) take tens of milliseconds.
- The upload, text reading and OCR run in the admin's browser, so keep that tab open until they finish (OCR carries on where it stopped if it doesn't). OCR keeps the computer awake only while its tab is in front; a long run with the tab hidden needs the computer set not to sleep.
- Page text and its search index take Neon storage, very roughly 5–15 KB per page: around 1 GB for 100,000 pages. Check the Neon plan's storage before a big upload.
- How much of a file the viewer fetches depends on how the PDF was made. Files from Acrobat and most publishing tools group their pages, and a page costs a few hundred KB. A file that lists every page directly under its root makes pdf.js read each page's entry when it opens, which can be most of the file for some converters' output.

## Diagnose

The **Diagnose** tab (`src/app/(app)/diagnose`) is an ongoing chat between a tech and Claude about one unit and one problem: "2019 RZR XP 1000, misfire under load, P0300", then later "checked plugs, still misfires, now it pops on decel". Each reply moves the diagnosis on: what to check next, in order, with specs and procedures from the shop's manual pages. It's for `diagnostics.work` (techs, managers, admins), including PIN sessions on bay tablets.

The tab opens on **Recent diagnoses**, the whole shop's, most recently used first, 8 to a page with **Previous**, **Next** and page numbers (just the first, current and last on a phone) and a "9–16 of 37" count; a page past the end shows the last one. The search box over it matches the title (which holds the complaint), the unit, its model number and VIN, who started it, and the customer whose vehicle it is (rows say "for Dana Whitfield" when one is linked): every word has to be somewhere, in any order and any case (`src/lib/diagnose-list-rules.ts` for the words and pages, `listSearchCondition` in `src/lib/diagnose-list.ts` for the SQL, run under `withShop` with one `ilike all` over those fields joined). Page and search live in the address (`/diagnose?q=belt+squeal&page=2`), so Back and shared links keep them. It's a plain GET form (Enter searches before the page's JavaScript has loaded); with JavaScript the list follows as you type, 300 ms after the last key, keeping the box's focus and every key, and a new search starts on page 1. **×** clears it, the count says how many match, and when nothing does it says so and offers to clear the search. A search with no letters or digits in it lists everything, and past 8 words the rest are left out (the count says so). If something else is tapped before a search comes back (a row, a tab), Next drops that search and the box goes back to the one in the address. Managers and admins also see **This month** above it.

### Three sources, labelled

Claude answers from three kinds of source and every cause and check says which:

1. **The shop's manuals**, searched and read through tools and cited to the page. A manual chip (book icon, **p.142**) opens the Library viewer at that page.
2. **The web**, through Anthropic's web search server tool: known issues, service bulletins, forum fixes. A web chip (globe icon and the site, **forum.example.com**) opens the page in a new tab.
3. **General knowledge**: Claude's own, shown as a **General** chip (lightbulb icon; "General knowledge" to screen readers) and never presented as a spec.

Specs (torques, pressures, resistances, clearances) are meant to come from manual pages: the prompt says so, and a check whose expected value has no manual page behind it is marked **VERIFY** (not from your manuals: verify before you rely on it). The server checks every citation before it's shown: a manual citation must be a page that a search or page read returned somewhere in this conversation (from the shop's own ready manuals), and a web citation must be a URL from this conversation's web search results (`finalizeReply` in `src/lib/diagnose-rules.ts`). Anything else is dropped; a cause left with no citation shows as general knowledge. Titles come from the tools, not from Claude, and model text is always shown as plain text (paragraphs and simple lists), never HTML.

### How a message works

- **Starting:** the quick form (unit model number with suggestions from the model list, such as "2019 RZR XP 1000 EPS — Z19VDE99AM", or Vehicle / Year / Model like the Library's filters; an optional VIN; complaint; fault codes, upper-cased as typed; what's been checked) or just a typed message. The unit sets the conversation's **manual scope**: the manuals the model list has for that model number (`findUnitManuals` in `src/lib/diagnose-tools.ts`). The panel says "Using 3 manuals for 2019 RZR XP 1000" and **Change unit** switches to another model number, a VIN or the whole library. A name typed in the model number box ("Sportsman 570", which its placeholder invites) is looked up as a name, and a year typed into Model ("2023 Sportsman 570") with no Year picked is the year, as `find_unit_manuals` reads them, rather than a word no model has. A VIN typed or pasted in the model number box (the frame's VIN plate has both) moves to the VIN box, with a note saying so; the server takes a VIN sent as the model number as the VIN too, so it's stored, shown and told to Claude like one typed in its own box.
- **The VIN** (`src/lib/vin.ts`, pure, so the form checks it as it's typed with the server's rules): upper-cased without the spaces and dashes people type or paste, and without a label in front ("VIN: 4XA…", "VIN# …", copied from a work order) or the leading I a barcode scanner reads off a Code 39 VIN label (no VIN has an I, so neither can be part of one); 17 letters and digits, never I, O or Q; the North American check digit in character 9 worked out from the others (49 CFR 565). The box has three looks for three outcomes. **Part of a VIN** (the last 6-8 characters, the serial number, which techs often have from a work order; or 12-16, a whole one with a character missing, which it says instead) is information: the box counts characters while it's typed, then says it isn't a whole VIN and goes with the diagnosis as a note, in muted text with an info mark, and the diagnosis starts; the opening message has it as `Partial VIN: MA765432 (8 of 17 characters)` (the opening card's VIN row says "part of a VIN, 8 of 17 characters"), Claude is told it can't identify the model, and it isn't stored as the unit's VIN. **A wrong check digit** is an amber warning ("Check the VIN: its check digit (the 9th character) doesn't match the rest, so a character may be off. You can still start."), and the VIN is used. **Something that can't be a VIN** (I, O or Q, more than 17 characters, other characters) is the only thing that holds the start up: the box gets an amber edge (`aria-invalid`), the note starts "Not a VIN:" and Start says beside it "Fix or clear the VIN to start." (the server refuses it too). A whole VIN is looked up as it's typed (`previewVinAction`, `previewVin`): "Matches 2021 SPORTSMAN 850 — A21SXZ85A1 · 1 manual", "Matches 2 variants of …", a model listed without a manual, or that no model in the shop's list has its code and it goes with the diagnosis as information; with Vehicle / Year / Model picked it adds that the VIN decides the unit. A model number for another model than the VIN's (their codes in characters 4-8, or their years, differ) is said under the box before the start and under **Unit and manuals** after it ("This VIN reads as a 2021, model code SXZ85; Z19VDE99AM is a 2019, model code VDE99. One of them may be off: check both on the frame.", `vinDisagreement`); model numbers from before 1997 can't be compared and say nothing. Polaris VINs carry the model code in characters 4-8 and the model year in character 10, and Polaris model numbers carry the same five characters in 4-8 and the two-digit year in 2-3 (Z19VDE99AM and a VIN 3NSVDE99_K…, A23SEE57A1 and 4XASEE57_P…), so the VIN looks up the shop's model numbers `_<yy><code>%`, any first letter. The year code repeats every 30 years (P is 1993 and 2023): the newest year that has a match in the shop's list wins. Checked against Polaris's full list: every model number from 1997 on is a letter, the year's two digits and five code characters (then up to two for paint and market), the two digits match the list's Year for 99.7% of entries, and a VIN made from each of 400 random model numbers finds that model and only its variants (about 17 ms). Older model numbers (W928627, 1985-1996) have a four-character code, so their VINs find nothing, and a code with I or O in it (R17RMAI4G8) can't be a VIN's. A VIN gives the model, not the paint, options or market, so it finds all of a model's variants (`A23SEE57A1`, `…A9`, `…B9`, …) and is one model number only when it fits exactly one: in 178 of the list's 2,338 year-and-code groups every model number shares one description (A and B market versions such as R22RSH99AG and R22RSH99BG, both "RGR CREW XP 1000 TRAIL BOSS - GHOST GRAY"), and a VIN can't pick between those either. The variants' manuals are the scope, no model number is stored, and the label is the year and the name they share ("2023 SPORTSMAN 570 EPS", or the whole description, paint and all, when they share one; `sharedModelName`), with every matching model number in what Claude is told. A VIN whose variants are listed without a manual is that unit too (all of them named), ahead of a Vehicle / Year picked as well and of a mistyped model number beside it (Claude hears about both). A VIN that matches nothing is kept as information. The model number wins when both are given and it's in the list, and Claude is told whether they agree. The VIN is stored on the conversation (`diagnosis_conversations.unit_vin`, checked by a constraint; `drizzle/0022_diagnosis_vin.sql`, and `0023_diagnosis_vin_grants.sql` lets `app_user` change it with the unit), shown in the opening card ("VIN") and under **Unit and manuals**, and given to Claude in the opening note with what it matched, to use for recalls and service bulletins: "on the web" only when the conversation has web search. Changing the unit by VIN sets it; changing to a model number it doesn't fit clears it (Claude is told: the tech said which unit it is); the whole library keeps it. When Claude itself looks up a model number the VIN doesn't fit, the VIN stays (it's the tech's, from the frame), the tool result tells Claude the two disagree and to ask the tech, and the panel says so beside the VIN.
- **The loop** (`src/lib/diagnose-loop.ts`): the app sends the conversation to Claude Opus 5.5 and runs the tools it asks for, then sends their results, until Claude calls `submit_diagnosis`. What the shop's own tools can reach is enforced in code, never by the prompt:
  - `find_unit_manuals({model_number?, vin?, description?, year?})` looks the unit up in the shop's model list (exact model number, whatever year is given with it, since a model number is one model of one year and the year a tech knows is often when it was sold, and the message says when the list has another year; then the VIN as above, also when it comes as the model number; then the model number's start; then year and model-name words, matched like the Library's Model filter, so in the manual's title too, and without the make; a year in the description is the year, whether or not one is given as well; with a year, the models whose own names have the words come first, and a title only counts when none does, so `2018 RZR S 1000` is that one model rather than every model its manual's title covers) and, when the manuals of every model it finds come to at most 60 (a unit, or at most a vehicle line), makes them the scope. Claude is shown the newest ten models and how many there are, but the scope is every matching model's manuals, so a name without a year (`Sportsman 850`: about 400 models from 2009 on) keeps the older units' manuals too, and a whole line (`Sportsman`, `Ranger`: over 100 manuals) is too many. Otherwise it says why and asks Claude to get the model number (it's on the frame or VIN plate), or the year after a name without one. A model number that's in the list but has no ready manual (its PDF isn't in the library yet) is reported as that model, so Claude can look up a closely related model by year and name instead of asking for the number again. A "model number" that reads as a name (with spaces, or no letter and digit in one word: "2023 Sportsman 570", "RZR XP 1000") is looked up by its words when it isn't a model number, instead of being reported as an unknown model number "2023SPORTSMAN570".
  - `search_manual_pages({query})` is the Library's full-text search (same index and syntax), limited to the scope and the shop's ready manuals, top 8 pages with snippets. When no page has every word (Claude's queries often add a word the manual doesn't use), it tries again in the scope for the pages with most of them, at least half (`searchManualsWithMost` in `src/lib/library.ts`): those with more of the search's fault codes and part numbers first (letters and digits together like `P0335`, or five digits or more like `2205187`: `isCodeTerm`; a code is what the search is most about, and dropping it as easily as a generic word would return generic pages first), then those with more of the words, then by rank, each with the words it has (`has_words`), and says so ("No page in the manuals this conversation is using has all of "P0335", "crankshaft"; these have most of them (has_words says which), and none of them has "P0335""). Phrases count as one word and `-words` stay excluded. "At least k of the n words" is written out as one tsquery (every way to pick k, ANDed, ORed together; at most 70 for 8 words), so the GIN index finds those pages like any search and only the scope's are counted and ranked (`tests/manuals.test.ts` checks the plans). Whenever the scope has no page with every word, the result also says how many pages in the shop's other manuals do, and in which (titles and counts only, never the pages): "Outside the manuals this conversation is using, 2 pages in the shop's library have all of the words, in a manual: … They aren't confirmed for this unit, so check one covers it before you take a spec from it; if the unit or its manuals are wrong, look it up again with find_unit_manuals." That's said even when the second try found pages in the scope, because a scope that's too narrow (the conversation behind this, scoped to three camo models' manuals, missed the main service manual) looks just like that. When the scope has nothing at all, it counts the other manuals' pages with most of the words instead, if none has them all, and says how many of the scope's pages have no searchable text (scanned pages OCR hasn't read, or pictures), which no search can find. The counts stop at 500 pages ("500 or more pages", naming some of the manuals without their counts), so a count of common words never reads tens of thousands of pages. Timed on a copy of Polaris's library (106,510 synthetic pages, local Postgres; the synthetic pages have more common words than real ones, so these are upper bounds): the second try within a unit's five manuals takes 0.1-0.5 s for a realistic 3-8 word query and up to 1.3 s for eight very common words with one missing; over the whole library (no unit identified) 0.4-0.9 s for realistic queries and up to 5.3 s for those eight common words, where about 78,000 pages have at least four of them and each is counted and ranked; the counts elsewhere take 5-100 ms (2.4 s before the cap). It only runs after a search finds nothing.
  - `read_manual_page({manual_id, page})` returns that page's text, up to 8,000 characters, only for a ready manual of the shop that's in the scope and only for a page it has.
  - `web_search` is Anthropic's server tool (`web_search_20260209`). `max_uses: 5` caps each API request, and the API enforces that. Across one tech message 5 is a budget rather than a hard cap: the prompt states it, and once a message has used it the loop tells Claude to stop searching, but a message whose first requests between them run more than 5 can go over (at most 5 per request, so 60 in the 12-request worst case). Turn web search off for the whole app with `DIAGNOSE_WEB_SEARCH=off`.
  - `submit_diagnosis` carries the structured reply: the chat message, the full ranked list of likely causes (title, the system of the machine it's in, Claude's confidence 0-100 and what it rests on, high/medium/low, why, open/ruled out/confirmed, how much work it is to confirm or rule out, sources), the next checks, the steps that confirm or rule out those causes (tier, what to do, the numbers of every cause it settles, expected values, sources), safety notes and questions for the tech. It's a strict tool rather than `output_config.format` structured output, because structured outputs can't be combined with citations and web search results always come with them; `tool_choice` stays `auto` (forcing a tool is a 400 on this model) and the loop asks once more if Claude answers without it.
- **Streaming:** `POST /api/diagnose/turn` streams NDJSON while Claude works ("Searching your manuals: P0300", "Reading page 142 — 2019 RZR XP 1000 Service Manual", "Searching the web: RZR XP 1000 decel pop", then the reply as it's written). If the browser goes away (a tablet sleeping, Wi-Fi dropping), the server finishes the message and saves it (`after()` keeps the function alive, up to `maxDuration = 300`); reopening the conversation shows it, and a page that isn't streaming a running message polls it. A tab that tries to send while another tab or tablet has a message running loads that message and follows it. Next keeps pages in `<Activity>` rather than unmount them, so the screens reset where they should: **New diagnosis** from a link always opens the quick form, even after a diagnosis was started there in the same tab (Back to that diagnosis still finds it as it was), and opening a conversation by a link (the Diagnose list) shows it as the server has it now, with whatever another tablet sent meanwhile, keeping an unsent draft. **Stop** asks the server to stop through the database; a stopped or failed message has **Retry**.
- **Time limit:** after 150 seconds the next tool results ask Claude to wrap up, leaving time for one full answer, and at 280 seconds the loop cuts off any request still streaming (the SDK's own timeout only covers the wait for a response to start) and ends the message as "took too long", with what it used saved, rather than letting Vercel end the function at 300 seconds before anything is saved. A response cut off at `max_tokens` isn't retried with more room when under two minutes are left.
- **Order: likelihood for causes, effort for checks.** The likely causes stay ranked by how likely they are (that's the diagnosis, and the callouts' numbers are those ranks), but the next checks go the way experienced techs work, so the quick fixes are ruled in or out first: **quick** (minutes, no tools or teardown: a visual inspection, connectors, loose or damaged sensors, wiring, fuses, grounds, fluid levels, stored codes), then **test** (a meter, pressure gauge, scan tool or Digital Wrench, or a road test), then **teardown** (panels, covers or parts off, swapping parts), and within a tier the most useful first: a two-minute check of a somewhat less likely cause comes before a likely one that needs teardown. The system prompt says exactly that; each check carries a required `tier` and each cause a required `check_effort` (how much work it is to confirm or rule out) in `submit_diagnosis`, both enums of those three, and each check the numbers of every cause it confirms or rules out (`causes`, an empty list only for a check that isn't about any one cause), since the screen shows each check in the cards of the causes it settles. The prompt and the tool's descriptions say so: the next checks are the steps that confirm or rule out the likely causes, at least one for every open cause (the quickest that settles it first), each with every cause number it settles, and a general check (stored codes, the battery's state of charge) is shown first, as "Start here"; a cause's `check_effort` is the tier of the quickest check given for it, since its effort words sit beside its steps. (Only descriptions changed, not the schema's shape, so every stored reply still fits it; a reply keeps up to 16 checks, each with all of its causes' numbers.) The reply check takes a value on the list (case, spaces and a few spellings aside: "Quick check", "tear down") and otherwise works it out from the words (`inferEffort`): teardown is a word that only means it (disassemble, split the cases, cylinder head, known-good part) or taking something off or swapping it in together with a part that's work to reach (a cover, the clutch, a belt, a wheel, a sensor or coil, spark plugs, the engine…; not an airbox or fuse box cover, a sensor's connector or a plug wire), so pulling a fuse, the seat, a plug wire boot or stored codes isn't; then test words (a meter, gauge, scan tool, the Digital Wrench, a road test, fuel pressure); then quick ones (looking, connectors, loose, fuses, codes, levels, the seat, the air filter); test when nothing matches. A bad value never breaks a reply, and the checks go in tier order, Claude's order within each. A check's cause numbers are kept when they're a cause's (the list leaves out a cause without a title, and the numbers follow), once each, in order. Replies saved before this have none of these: their checks show as one list in Claude's order and their causes say no effort; replies saved before checks carried causes keep their checks in a **Next checks** list of their own (below). Changing these changed `submit_diagnosis` and the prompt, and rewording them for each cause's steps changed them again, with the effect on open conversations described under Model and settings.
- **Confidence.** Each likely cause carries a required `confidence`, an integer 0-100 for how likely it is behind the symptoms given everything so far (the causes needn't add up to 100), and `based_on`, what that rests on (`tech_report`, `fault_codes`, `step_results`, `manual`, `web`, `experience`). The prompt asks Claude to rank the causes by it and to work it out again with every reply from what's new (checks that came out fine or found a problem, causes ruled out, new symptoms or codes), and gives the bands its likelihood follows. Strict tools can't take a minimum or maximum, and the streamed input isn't held to the schema anyway, so the reply check rounds it and holds it to 0-100 (a number sent as text such as "72%" too; anything else leaves the cause without one) and keeps only the listed `based_on` values, once each (`confidenceOf`, `basedOnOf` in `src/lib/diagnose-rules.ts`). A cause with a confidence gets its likelihood from it, high from 60, medium from 30 to 59, low under 30 (`likelihoodFor`), so the heat bar, the unit's glow and callouts and the % never disagree; the causes keep Claude's order (the checks and the tech refer to them by number). Replies saved before this have no confidence and show no %. Adding these changed `submit_diagnosis` and the prompt (see Model and settings).
- **Feedback:** each cause has **Ruled out** and **This was it**. Claude hears about them with the next message (as an app note), and "This was it" records the conversation's outcome (the cause, its likelihood and rank) for AI-accuracy figures later.
- **Check-off:** the tech ticks each step off as it's done and can say what it found, **OK** or **Problem found** (`markStep` in `src/lib/diagnose.ts`, the same people as can mark a cause). Every tick is saved with the conversation (`diagnosis_conversations.step_checks`, `drizzle/0024_diagnosis_step_checks.sql`; `0025_diagnosis_step_checks_grants.sql` lets `app_user` change it), so the bay tablet and the office PC show the same. A check is known by its words (case, accents, punctuation and spacing aside, though signs such as < > = + count; `stepKey` in `src/lib/diagnose-step-checks.ts`), so a check that settles several causes is ticked in every card, and one Claude gives again in the same words stays ticked (a check Claude gives twice in one reply, once for each cause, is one check, for all its causes). Claude hears the ticks with the next message, in the same app note as the presses: "Since your last reply the tech checked: - “Measure coil primary resistance…” (for cause “Ignition coil…”): OK (found nothing wrong)" (or "problem found", "done (no result given)", "unticked (not done after all)"), each check once, as it stands, and only when that isn't what Claude last heard. As with presses, a tick Claude hasn't heard yet is replaced by the next one on the same check, and one taken back before Claude heard it leaves nothing; once Claude has heard, a change is a new entry. While a message is with Claude, ticks are only added (the ones on their way stay), so a tick taken back then isn't lost: Claude hears it with the message after. Each tap carries how the check stood on the screen it was made on: when another device has changed it since (the bay tablet's **Problem found**, on an office PC that hasn't reloaded), nothing is saved and that screen gets how it stands now, saying so under the step, rather than wipe out what the other one said. The prompt says what these notes are and to use them to update each cause's confidence and status (an OK counts against the causes a step checks, a problem found for them, and Claude asks what was found when it matters), and to repeat a check word for word so its tick carries over, or to word it as a new check when the tech should do it again (a road test after a repair). Adding this changed the prompt, not `submit_diagnosis` (see Model and settings).

### The screen

The diagnosis is meant to read at a glance, in the calm, plain manner of OEM service information (Polaris's own manual figures, Digital Wrench, Snap-on and Bosch diagnostic software) rather than a game: separate cards with a plain sentence-case header, a muted icon and a count, the app's dark theme with its teal accent kept for actions and the one system picked. Nothing on the screen glows, pulses, spins or animates, even while Claude works (a still working mark and the step's words say so):

- **The unit:** a header with the unit's name and paint (a swatch of it), a **Solid | Phantom** switch and **Expand**; below it the unit as a shaded 3D model of the actual machine (its line, seats and colour) on a light neutral plate, its suspect systems called out with numbered circles like a service manual's figure (just the numbers where the names won't fit), and a key underneath (below). Where WebGL isn't available it's the line drawing instead, in the same style.
- **Likely causes**, the main card: rank, title, likelihood as a three-segment meter with Claude's confidence right after it while the cause is open ("72%", in a fixed width so the bars line up; none on a confirmed or ruled-out cause, or on a reply saved before causes carried one), and under the title one quiet line of what it rests on, built from the citations the server kept and Claude's `based_on` (`evidenceParts` in `src/lib/diagnose-evidence.ts`: "1 manual page · 1 forum post · your report · fault codes"; web pages are forum posts or web pages by their address; manual or web in `based_on` count only with a citation that held; "general knowledge" when there's nothing else), a **New** tag on causes that weren't in Claude's reply before, a status chip only when it isn't open (Confirmed, Ruled out), how much work it is to rule in or out as quiet words leading its why line (**Quick to rule out**, **Needs a test** or **Needs teardown**, with a stopwatch, meter or wrench mark), so the cheap suspects stand out at a glance without another row of chips (the chips are buttons and links, and an effort chip looked like one and pushed the source chips onto a second row), and only while the cause is open, the system it's in (a chip that picks it on the drawing, bringing the drawing into view if it has scrolled away), "why" on one line (tap for the rest), source chips, its steps (**How to check**, below), and **Ruled out** / **This was it** toggles with small pictures of the manual pages it cites at the end of the same row (below). A confirmed cause moves to the top and stands out; ruled-out ones sink to the bottom as one dim line each (tap the title for the rest): "Ruled out by Claude", or the tech's own "Ruled out" with **Undo**. A press keeps the page where it is (the cause moves, the view doesn't, even at the end of the list, where a card folding up would otherwise pull the page down: the panel gets that much room at its foot, below both columns, until it's scrolled out of sight; from the keyboard the focus follows it). Until Claude has heard about a press, the tech's own press decides where a cause sits and how its system glows. Everything to tap is at least 44px tall for gloved hands: chips are 36px to look at and reach 44px to tap.
- **How to check**, in each open cause's card (`src/lib/diagnose-cause-steps.ts`): the checks that confirm or rule that cause out, quickest first (quick, then test, then teardown; Claude's order within a tier), numbered 1, 2, 3 within the card as a list's "1." rather than in a square, so they aren't taken for the causes' numbers. Each step has its tier as a small tag (the stopwatch, meter or wrench mark and **Quick**, **Test** or **Teardown**; a quick one brighter and bolder, so the quick steps stand out from card to card), what to do, the expected reading or spec as a monospace chip (each number kept on one line with its unit) beside the manual and web pages it cites, and where the spec or procedure comes from at one of three levels (`sourceLevel` in `src/lib/diagnose-evidence.ts`): **Manual**, a page of the shop's manuals the server matched; **Web**, a web source and no manual page; **General**, Claude's general knowledge, to verify first. A spec carries the level as its chip's label, teal **MANUAL** or amber, dashed **VERIFY** (a spec with no manual page behind it is general even when it cites the web: the web is for patterns, not specs; amber is kept for a number to check, so an unchecked one never looks like a manual's). A step without a spec shows its level by what it cites: its teal manual page chip or its web chip, or, citing neither, a quiet dashed **General** tag at the end of its words (muted like a cause's General chip, not amber: most quick looks are general knowledge), so it costs no row (no **General** chip on a step either, which would cost most steps a row and cites nothing), and small pictures of the pages it cites that the card doesn't show already; a short step's chips share its line. A check that settles several causes is in each of their cards, so each card is complete on its own, with a quiet "Also checks cause 3" (or "causes 2 and 4", in the list's small squares) so one test is done once. Checks for no cause in particular (stored codes, the battery's state of charge; or numbers that all point past the list) are a **Start here** block at the top of the list, before cause 1, "covers every cause, quickest first". An open cause no check settles yet says "No check from Claude yet" with **Ask how to check**, which puts "How do I check cause 2, Fouled or worn spark plugs?" in the message box (after anything typed; on a tablet or phone it opens the Chat tab) without sending it. Ruled-out and confirmed causes show no steps, so ruling a cause out hides its steps (and the list stays where it is on screen). The full-screen view's sheet shows each cause's steps too, before its large pictures. Every step (in the cards, Start here, the sheet and an older reply's list) ends with its tick, a 44px box at the right end of its row (beside its chips when they leave room), and once it's ticked **OK** | **Problem found** beside it, 12px clear of the box so a near miss doesn't take the tick back (optional, 44px; tap the pressed one again to clear it, tap the box again to take the tick back); screen readers hear each box by its step's words ("Done: Unplug the speed sensor connector…"). **Next** marks the first step not done in each list, quickest first: the word is part of the box's button (tapping it ticks the step), and the step's number turns teal. A done step stays where it is, dimmed, its box checked. Only the next step keeps room for the two result buttons while it isn't done, so ticking steps in order moves nothing above the next one (the step after it takes that row when it becomes next); any other step has just its box, so steps cost no row of their own for it where their chips leave room. A tick shows at once and is saved behind it (the app sends one at a time); when it doesn't go through, including a request that never gets an answer (the Wi-Fi dropped, or the app was updated since the page loaded), it goes back as saved, with the reason under that step, where the tech is looking; the saved copy is what a reload or another device shows. Once a cause is marked **This was it**, the causes still open are set aside, as the drawing tones them down: their % muted, and no step says **Next** or suggests a mark. When every step of an open cause is done and OK, a small "All steps OK" tag on its **Ruled out** suggests it; a problem found on any of its steps puts "Problem found" on **This was it**. Neither is ever pressed for the tech. "Claude hears about your marks with your next message." counts ticks too; it comes under the last list (the causes, or an older reply's **Next checks** below them), so it never pushes a list down. A reply saved before checks carried causes keeps its **Next checks** card as it was: under tier headers (**Quick checks** · minutes, no tools; **Tests** · meter or scan tool; **Teardown** · parts off), numbered on across them as **Step 1**, **Step 2**… (`checkGroups`), or one list for a reply from before tiers, each with its source level as above.
- **Safety:** a compact amber banner, one line per note, right under the unit (beside it on wide screens, before the causes on narrower ones) so it's among the first things a tech reads.
- **Unit and manuals:** "Using 1 manual for …", the VIN when there is one (with a note when its check digit doesn't match, and an amber note when it's for another model than the unit's model number), **Which manuals** and **Change unit** (a model number or a VIN).

In the thread Claude's reply stays, tighter, and the conversation folds so a tech never scrolls past the symptoms to reach the current answer: the latest exchange is open (and, while a new message is running or after one that failed, the last one Claude answered), and each earlier one is a two-line row, the tech's first line ("Mike: Misfires under load, worse when hot (P0300)") and Claude's ("Claude: 3 causes, top: Ignition coil breaking down under load"), that opens on a tap and folds back (`src/lib/diagnose-thread.ts`). What Claude looked at is small icon chips (manual searches, pages read, web searches; tap for the steps, and screen readers hear "Searched your manuals 2 times · read 1 page · searched the web once"). **Claude asks** questions are buttons: tapping one drops it into the message box as a short quote (`> How many hours are on it?`) to answer under (above whatever was already typed, which is taken as the answer; after earlier quotes, as a block of its own), and the sent message shows it as a quote. The quick form's opening message shows as compact labelled rows (unit, VIN, complaint, codes as chips, already checked). Every card in the thread, the tech's messages and Claude's replies alike, takes the column's full width with the same padding, so their left and right edges line up with the folded rows and the message box at every width; the tech's are told apart by a bar down their left side (an inset shadow, drawn inside the card so the edges stay put), a person mark by the name and a lighter fill, not by a chat bubble's offset, and the folded rows have the cards' corners and side padding. There's no cost per message in the thread any more: the cost is still recorded per message and conversation, and managers still see the month's total on the Diagnose tab. (A message's JSON still has `costCents`, always null, for one more release: a page loaded before this change shows a cost whenever it isn't null, and showed "≈ $NaN" without it.)

On narrow screens (a bay tablet in portrait, a phone; under 1024px) the diagnosis and the chat are two tabs under a sticky **Diagnosis | Chat** switch, rather than the diagnosis panel sitting below a long thread: the drawing and the top causes are what the tech comes back to between checks, and the switch keeps both one tap apart without scrolling past the thread. A conversation with a reply opens on Diagnosis, a new one on Chat (where the progress shows); the drawing and the top cause's title fit the first screen of a phone (390×844) and a tablet. New things are still noticed, in the sticky switch itself wherever the tech has scrolled: while Claude works the Chat tab says **Working** beside a still mark (and the top of the Diagnosis tab what Claude is doing, with **Open chat**); when a message ends on the tab you're not on, the Chat tab says **New reply**, **Stopped** or **Not sent**, the Diagnosis tab **Updated**, the top of the Diagnosis tab says so too (**Claude replied — Read the reply**, or that the message was stopped or didn't go through), and the latest reply has **See the diagnosis**. These use teal and amber: red is kept for suspect parts. Claude's questions and a full conversation's **Start a new diagnosis for this unit** also show on the Diagnosis tab, with the 3D unit at its top. On wider screens the diagnosis sits beside the conversation's heading and thread from the top, sticky, scrolling on its own, so the unit and the top causes are on the first screen of a 1180×820 tablet and the office PC. The conversation page uses the screen's whole width (up to 1888px; the header widens with it), where every other page keeps to 1024px (the conversation marks itself `data-wide-page` from a layout effect, so the mark is there only while it's shown: Next keeps a page it navigated away from in the document, hidden, and a mark left behind would widen the next page too; `has-[...]` variants in the app layout and header). From 1280px wide it's three columns: the thread (folded, as above), the causes and checks, and the unit with the manual pictures (sticky beside the causes), so nothing that matters sits below the first screen when there's room beside it; 1024–1279px is the thread and one diagnosis column with the unit at its top.

### The 3D unit

The unit is a shaded 3D model of the machine, built in code with three.js (pinned in `package.json`) and drawn in WebGL: Polaris's manuals have exact pictures of parts but no whole-vehicle model, so the machine itself is modelled (`src/lib/unit-3d/`) and the manual pages supply the real pictures (below). It's loaded with a dynamic `import()` from the conversation page only (no other page's JavaScript has three.js). Until it's ready, and wherever WebGL isn't there, fails to start or loses its context, the line drawing shows in the same box (below), which is also what the server sends, so nothing jumps.

**Which machine.** One model family per Polaris line, proportioned from Polaris's figures (wheelbase, length, track, tyre size; `layout.ts`): **RZR** (sport side-by-side: low and wide, long-travel A-arms and trailing arms with radius rods and piggyback shocks, a raked cage with a black roof and rear braces, bucket seats, a sculpted hood with slim LED lights, open at the back over the engine with a small rack; RZR 4 is four seats and a longer cage; RZR 570 and Trail are mid-size, RZR 170/200 youth), **Ranger** (utility: upright cab and cage, bench seat, flat dump bed, brush guard; Crew 4, 5 or 6 seats and longer; mid-size 500/570 two seats; Ranger 150 youth; Ranger 6x6 a third axle), **General** and **ACE** (crossover: sporty stance, small dump box; General 4; ACE one seat), **Xpedition** (enclosed cab with doors and glass, a box; XP 5 / ADV 5 five seats), **Sportsman** (utility ATV: wide fenders with front and rear racks, handlebar headlight pod, floorboards; Touring / X2 two-up seat; 6x6 and Big Boss a third axle and a bed; youth 90/110 smaller), **Scrambler** (sport ATV, no racks, fenders turned up at the ends; also Predator, Trail Blazer and the adult Outlaw), youth **Outlaw** and **Phoenix** (small sport ATVs), and a **generator** (an open-frame portable). Line, seats, size and a third axle come from the unit (`specForUnit` in `src/lib/unit-vehicle.ts`, pure and tested): the model list's descriptions for its model number ("RZR XP 4 TURBO EPS GHOST GRAY", "RANGER CREW XP 1000 NS ULT - SUNSET RED MTL", "SPORTSMAN 6X6 570 - SAGE GREEN") are the most exact, since the first RZRs are listed under the Ranger's code and the ACE (a side-by-side) under ATV; then the model number's brand codes; then the titles of the manuals that list it; then the brand codes and titles of the manuals in use; then the words in the unit's name; then the usual line for the kind of vehicle. `unitMachine` in `src/lib/diagnose-tools.ts` gathers those from the shop's model list (shop-scoped like everything else) and the conversation gets `model` (and `vehicle`, for the drawing) with it. Polaris lists the 2009–2010 RZR 170, a youth side-by-side, only under ATV, so when the codes say ATV but the unit's name (or, for a model number listed without one, its manuals' titles in the list) says RZR, Ranger or General, it's a side-by-side; no ATV in the list has those words.

**The right way round.** The models are written with the machine's left (the driver's side, where a Polaris has its CVT) on +z, and three.js's camera looks down −z with +x forward, which would put that side on the picture's right: a mirror image. So each machine's shapes are mirrored as they're built (`buildGeometry` in `build.ts`: z flipped, triangle winding turned back) and every label point goes through the same flip (`worldPoint` in `layout.ts`). From **Left** the front points left and the clutch cover shows; from **Front** the driver's side is on the picture's right; the diagnosis screen's three-quarter view is from the front left. The tests check both, and the end-to-end checks look for the radiator's and the clutch's callouts on the right sides of the picture.

**Its colour.** Painted parts take the unit's real colour from the model description (`src/lib/unit-paint.ts`, tested against descriptions as Polaris writes them): the named colours (Sage Green, Indy Red, Solar Red, Sunset Red, Onyx Black, Titanium, Velocity Blue, Avalanche Gray, Ghost Gray, Lime Squeeze, White Lightning, Bright White and about 80 more), Polaris's shortenings (S.GREEN, SGRN, PNTD RED, BLK, WHT, A.CRYSTAL, W.LIGHTNING, PPC), names the model list cut off at 40 characters ("STEALTH GRA", "MATTE TITANI"), finishes (matte, metallic, pearl), two-tones (RED/BLK, BRIGHT WHITE/INDY RED, GREY W LIME: the second colour on the accent panels) and camouflage (Polaris Pursuit Camo and others as a printed pattern drawn in code). A description with no colour (about one in seven on Polaris's full list, mostly old or international models) gets a neutral gray. Frame, trim, floor and plastics stay black or charcoal. Checked against Polaris's whole model list: more shortenings (STLTH GRAY, INRED, POLARIS PUR CAMO, M NARA), colours run into the next word (N. BLUEEV, GRNBLK), and things that aren't colours (a bare MAG is a Magnum, RD COM is Ride Command, NON MTLC isn't metallic, a generator's "CAN BL" isn't blue); a two-letter colour the list cut off ("MATTE BL": blue or black?) counts for nothing. Seats come from the same words ("1000S4" is a four-seat RZR S).

**How it looks.** Like a manufacturer's studio shot with a technical illustration's line-work (`viewer.ts`): calm studio lighting (a soft key from the front left and above, a cooler fill, a rim from behind, a hemisphere light and a studio environment, `RoomEnvironment` through PMREM), Khronos PBR Neutral tone mapping so the paint reads true, satin paint in the unit's colour (a light clear coat; metallic, pearl or matte as Polaris names it), matte textured black plastics, a satin black frame, brushed and cast metal, dark rubber, vinyl seats, glass, and light lenses that are just lenses (nothing on the unit is emissive). It sits on a light neutral plate (`.unit-plate`, a quiet radial grey from #e6e8eb to #c8cdd2, so dark lines, the paint and the callouts read as in a manual's figure; `PLATE` in `look.ts`, which the contrast tests use) with a soft contact shadow under it, rendered once per machine from below into a picture shaped like its footprint, blurred in several passes each a step wider (a smooth fall-off, no stripes from the frame rails) and faded out at its edges, a tight one where it meets the ground and a wide faint one (`shadow.ts`). Fine edge lines of one weight (about a CSS pixel at any pixel ratio) give the CAD finish (`edges.ts`): the parts are drawn a second time into a target as surface direction, part number and depth, and a full-screen pass draws each silhouette, where one part meets another and creases, on the nearer side only so they stay one line wide. Each kind of part says which creases get lines: all of them for the bodywork and parts, only sharp ones for a flagged part's flat colour (so its facets don't crackle), none for a flagged tyre (its outline, not every tread block). The target is twice the size (supersampled) only on a screen under 1.25 pixels per CSS pixel, and only while that stays within the canvas's 2.4 million pixel budget (`supersampling`, tested); a 1280×800 tablet at 1.5× full screen draws 1.96 million pixels for the canvas and the same for the lines. The bodywork is moulded as continuous skins lofted through cross sections with crisp creases (`loft`, `crossRing` and `sweep` in `geo.ts`; the arch cut-outs in `shells.ts`): each line's own front (the RZR's low, pointed nose and slim lights under a sculpted hood; the Ranger's and General's upright grille and brush guard; the Sportsman's nose fascia under its rack), fenders swept over the tyres along their arcs with black liners, and a rear clip; an ATV's fenders are wide swept decks. A youth unit is a child's machine, not a shrunk adult one: shorter ends, a taller cage for its size, a wider stance. Tyres are turned carcasses with raised tread lugs, rims are cast faces with spoke windows, a hub and a beadlock ring, with the brake disc behind (`wheel` in `parts.ts`); cages and racks are tubes, the side-by-sides a moulded, domed roof, springs are coils. Each system's parts are merged per material: a machine is 29–58 meshes (the generator 29, the ATVs 53, the side-by-sides 57–58) and 11,000–64,000 triangles (`tests/unit-model.test.ts` keeps every full-size line under 70 meshes and 75,000 triangles). A frame of the card is about 115–130 draw calls and 85,000–150,000 triangles drawn (the parts, the phantom body's depth pass, the flagged parts' see-through copies and the edge pass drawing them again; the generator 64 calls and 22,000 triangles), measured in SwiftShader. It draws only when something changed or while the camera moves, not at all while off screen, in a hidden tab or under a manual page opened full screen, caps the canvas at about 2.4 million pixels (the lines' target with it), and frees its GPU memory (and its WebGL context) when the page goes, including when Next keeps the page hidden in its cache. It's built a step at a time (paint, shapes, meshes and edges, then the shaders compiled), with a frame for the browser between steps, and the last three machines' shapes are kept, so going back to a unit doesn't build them again. If the browser takes the WebGL context away (a GPU reset, too many tabs), the drawing shows until it's given back and the unit is then built again in a new context (after three losses the drawing stays). three.js needs WebGL 2; without it the drawing shows.

**Systems inside it.** The 18 systems are real parts in their real places (engine, airbox, coils, header and muffler, radiator and hoses, battery and starter, ECU and harness and lights, CVT cover, gearbox, diffs and half shafts, brake discs and calipers, steering column, rack and tie rods, A-arms and shocks, wheels, frame and cage; `models/sxs.ts`, `models/atv.ts`, `models/generator.ts`), each with a label point (`layout.ts`; the tests check every line has one for each system, on its own parts). Flagged systems use a service manual's phantom view (`look.ts`): once anything is flagged the body keeps its real paint but turns partly see-through with its edges drawn (**Phantom**, the default then; **Solid** puts the body back), so it still looks like the owner's unit, and the parts inside that aren't flagged step back to light neutral greys. The phantom body's paint is the unit's colour lightened and greyed toward the plate (`phantomPaint`), so a red unit's body never reads as a flagged part (the tests keep a CIE colour difference of over 35 between them). The flagged parts are drawn solid and opaque in flat, clear colours with a dark outline: deep red for high and for confirmed (confirmed also gets a small check badge on its callout), amber for medium, only a red outline for low, neutral grey for ruled out (its marker in the key); once a cause is confirmed the other suspects are toned down to pale tints. The body never tints a flagged part: it's drawn once over what's behind it (a depth pass first, so overlapping panels don't stack) and not over a flagged part (the stencil those parts leave). A flagged part behind something else (the seats, the engine, a tyre) still shows: a see-through copy of it is drawn over whatever is in front, with its outline, so from every view the colour is where the callout points. Wheels/tires flags the front tyre on the near side, not all four. Callouts are HTML over the canvas, placed from the parts' projected points with the drawing's rules (bands above and below the machine's outline, never over each other, leaders never through another callout) and always inside the plate (`fitCallouts` in `src/lib/unit-graphic/callouts.ts`, tested at phone to desktop sizes): a thin dark leader from a dot on the part to a small numbered circle, the number the cause's place in the Likely causes list (`rank` on each system's state: its confirmed cause, else its first one still open), with the system's short name (with a soft halo in the plate's grey, so it reads over the machine when zoomed in; no pill) and the list's three-bar likelihood meter beside it ("1 Ignition"), so colour is never the only signal. Where the names won't fit, and on any card under 420px wide, a callout is its numbered circle alone and the key names it. A confirmed system's check sits after its number (or on the circle's corner when it's a number alone), never over it, and the rings and numbers meet WCAG contrast on the plate. A part off the canvas or behind the camera gets no callout. On the card each callout is a button that picks its system (its causes highlighted); it doesn't open the full-screen view. A tap on any part of the machine, flagged or not, opens the full-screen view on that part's system with its sheet (see **The part sheet**): the tap is cast into the scene and takes the part seen there, through the body's panels (they aren't a system), so a part seen through the phantom body is the one tapped, and a flagged part drawn through what's in front of it (a tyre, the engine) is that part, not the one it shows through; a finger gets about 10px of slack toward a flagged part. On the card it's the tap's click that opens it, so a touch that only stops the page scrolling doesn't. The key's phantom line says a part can be tapped. On a mouse the cursor shows where a part can be tapped and the system's name sits by the pointer (one raycast a frame at most, nothing redrawn). The key underneath lists them by number with the likelihood in words ("1 Ignition High", "3 Fuel Low") and the ruled-out systems with their marker. The canvas is a `role="img"` whose label names the flagged systems. On the diagnosis screen it's a still three-quarter view from about eye level; a finger on it scrolls (or zooms) the page; reduced motion stops the camera flights.

**Examine.** **Expand** opens it full screen on the same light plate: drag to turn it, pinch or scroll to zoom, two fingers or right-drag to move it, **Reset**, **Front / Rear / Left / Right / Top**, **Solid | Phantom**, and keys (arrows turn, Shift+arrows move, + and − zoom, 1–5 the views, R reset, P phantom or solid, Esc back). Tapping any system (flagged or not) or its callout flies the camera to it (the hint under the stage says so first; a shorter one on a phone or tablet), from the side that shows it best (of the directions round it, the one with the fewest other parts between the camera and the system, so it isn't behind the body, the seats or a wheel) and close enough to fill the stage, and opens a sheet beside it (below it on a phone or a portrait tablet; beside it and wider from 1280px, so a manual page and what it says fit side by side): **From the manual** (see **The part sheet**), then that system's causes, whose **Ruled out** / **This was it** work as in the list, with pictures of their manual pages. The view is in the address (`?examine=unit`, `?examine=ignition`), opened with the native history API, which Next's router follows without fetching anything, so the browser's Back or Android's back gesture closes it, and a page Next brings back from its cache never comes back with it open (`use-history-param.ts`). The callouts stay on the stage, clear of its tools and the sheet; with a system picked its callout keeps its name and the others are numbers. On a phone the whole machine fits the stage when it opens and after the sheet opens below it, and the five views are behind one **Views** button so a row of them doesn't cover the unit. The same WebGL context serves both views: the canvas moves into the full-screen view and back. The full-screen views (and a manual page opened full screen) open in `#app-overlays` inside the app's shell, mounted after hydration (so an address with `?manual-page=` renders on the server like any other): the page behind them is held inert, and a bay tablet's idle lock, which makes the whole shell inert, covers them too; unlocking leaves the page behind held until the view closes.

### Manual pictures

Every cause and check that cites manual pages shows small pictures of those pages, and the wide layout has a gallery of the reply's pages beside the unit (the picked system's when one is picked). They're the real pages, drawn in the browser by pdf.js through the viewer's own loader (`storage-pdf.ts`) and link action (`getManualFileUrl`, which checks the manual is one of the shop's ready ones and hands out a 15-minute link, renewed when storage turns one down), only once they're near the screen, two at a time, from one open copy of each manual (all through one shared pdf.js worker, closed with the last copy), and kept as small images so each draws once (`src/app/(app)/diagnose/manual-pages.ts`); everything is let go 30 seconds after the page goes. A page that can't be drawn says so and retries on a tap. Tapping a picture opens the page full screen (`?manual-page=<manual>:<page>`, closed by Back; with `:torque`, from the part sheet's card, it opens zoomed toward the page's TORQUE boxes: each TORQUE heading in the PDF's text layer and the lines under it, at most 3x, unless the tech has zoomed already; with `:box-<left>-<top>-<right>-<bottom>` (thousandths of the page), from one of a part's drawings, it opens zoomed so that drawing fills the screen, at most 4x): pinch, scroll or the buttons zoom (redrawn sharp at the zoom once it stops), drag moves it, and **Open in manual** goes to the viewer at that page (`/library/<id>?page=N`).

### The part sheet

Tapping any part of the unit, flagged or not, opens its system in the full-screen view (`?examine=<system>`; on the card a tap on a callout still only picks its system), and the system's sheet starts with **From the manual** (`src/app/(app)/diagnose/part-sheet.tsx`): the system's parts as chips to pick from (44px to tap, the first picked), the picked part's best manual page drawn large (half the sheet where the card sits beside it, a landscape page in its own shape; tap it to open the page full screen to zoom into, as any manual picture; **Open in manual** goes to the viewer at that page), up to three more pages that show it under it as small pictures (**Other pages**: a tap draws that one large instead; on a phone they come right under the page, so the change is in view), and beside the page (under it on a phone) what the page says: the procedure's title, the special tools as the page prints them, and which page of which manual it is. Its steps, torque specs and cautions are never put on the card: when the page has any of them, one line in the teal of a manual spec says "Steps, torque specs and cautions are on this page", and **Read them on the page** (44px) opens the page full screen to read them there, zoomed toward its TORQUE boxes where the PDF's text layer says they are when it has torque specs (`?manual-page=<manual>:<page>:torque`; a scanned page, with no text layer, opens as it is). See **What the page says** for why. While a page is read the first time, a line says so and the page is already there to look at (a screen reader hears when the card arrives); a page being read on another device is asked for again every 2 seconds, for up to two minutes. While another part's sheet comes, the last one stays, dimmed. **Causes · N** by the heading goes down to the system's causes (on a phone they're below the page and its card). A part no page is about (the frame, named only in another part's procedure: "Remove the two fasteners securing the starter solenoid to the frame") gets the pages that name it, said so, the best one without a card (it's another part's page; one the tech picks from **Other pages** has its card, as anywhere), and a **Search the Library** link. Where the page can't be read (no API key, the shop's daily readings used, a failed read) the page shows with a quiet "Couldn't read this page's details", and the screen doesn't ask again until it's loaded again. No manual for the unit, or nothing in its manuals with the part: the sheet says so, with a **Search the Library** link for the part. A system with no causes has the same sheet, without causes. The sheet comes from `POST /api/diagnose/part-sheet` (`src/app/api/diagnose/part-sheet/route.ts`, for `diagnostics.work` like the rest of the diagnosis; `src/lib/diagnose-part-sheet.ts`): a route rather than a server action, since the browser runs a page's server actions one at a time and a tick on a step would otherwise wait behind a page being read. The screen keeps what it was sent for the visit, so going back to a part or a page asks nothing again; changing the unit asks again. A page's card is its own request, which only checks the page is one the conversation can reach, without the search.

**The part's drawings.** Above the page, **From the manual** shows the part's drawings cropped out of its manual pages, large: the first across the sheet (as tall as about two thirds of the screen at most, centred; lower in the examine view, where the bubble on the unit shows it too, so the page and its card stay in the first screen), the others in a strip under it (a tap shows that one large), each with "Exploded view · p.N" or "Drawing · p.N" and **Zoom** under it (nothing is drawn over a drawing: an exploded view's callout numbers reach its corners). A tap on the large one, or **Zoom**, opens its page full screen zoomed to it (`:box-…`, above); the whole page stays a tap away as before (the page, **Zoom**, **Open in manual**, **Other pages**). The server names the pages to look on (`drawingPages` in `src/lib/diagnose-parts.ts`, up to four): the part's exploded views first, pages of the conversation's manuals with the part on them and a view's heading (a line that reads as a heading: short, in capitals or with its words capitalised, no step number or full stop; EXPLODED VIEW, ASSEMBLY VIEW, COMPONENT VIEW, or the part's own name with VIEW: "TRANSMISSION VIEW", which counts most; a step or a note that points to a view, "Refer to the exploded view on page 8.12", isn't one); then pages with a drawing's callout numbers and no such heading (lines of nothing but numbers counting up from 1), called drawings; then its procedure page (its best page, a procedure still when it has callouts too); then the other pages a cause cites for it. Never a page that only names the part on the way. They're found in the same query style as the part's pages (`searchDrawingPages` in `src/lib/library.ts`, one query): only the best ranked pages with the part's words, and the best ranked of those with the word "view" (the index says which), have their text read, those with a view's heading first (an exploded view's, or one naming the part: "TRANSMISSION VIEW" or "Transmission View", ahead of a figure's "TOP VIEW"), so a part's exploded view is found however many of its procedure pages name it more often (a General's transmission). The browser finds the drawings on each (`src/lib/manual-figures.ts`, through the same shared pdf.js worker and storage reader as the page pictures): it follows the page's own operations (pdf.js's operator list: the transform through q/Q, `cm`, forms and their boxes, clips) to where each image is painted, keeps those at least 12% of the page across and down and 4% of it in all, joins images that touch (tiles of one picture), takes in the callout numbers printed around one (its text layer's lone numbers within 6% of the page), and orders them largest first; each is then drawn alone at the size it's shown (only that part of the page is rendered, at no more than the scale the whole page would fit a tablet's canvas at, about 5 times a Letter page: pdf.js draws a stencil image anywhere on the page whole at that scale) and kept for the visit, without holding up the 3D view, and the page's decoded images are let go once it's drawn. Pictures on the screen are drawn before drawings are looked for (a part's pages are looked at one at a time, so the large page's picture, asked for meanwhile, starts straight away on slow storage too), a part's pages are shown as each is looked at, and the pages of a part the tech has left aren't looked at. A page with nothing to crop (a drawing made of lines, or a scan that's one image over the whole page or nearly: 85% of it or more) is shown as the page: an exploded view as its page in the strip, unless it's the page already drawn below; otherwise the sheet is as it was.

**On the unit.** In the examine view (Solid or Phantom) the part picked gets the same drawings in a bubble on the 3D unit itself (`src/app/(app)/diagnose/drawing-bubble.tsx`), so what it looks like in the manual is right there by the part: the part's name and page ("Starter motor · p.9") with "From the manual" and the kind (exploded view or drawing) under it, the first drawing (an exploded view first; one with nothing to crop as its page), **Enlarge** under it, and with several, arrows, a count ("1 / 3"), a swipe and the arrow keys between them. It sits in free space beside the part, off all of it (the box round the part's shape near its callout point, as each frame has it, its shapes cut to that box where they cross it, a steering post or a frame's tubes with their ends well outside it, and grown by as much as its points can be off its shape, so it holds all of the part however close the camera: a General's transmission, engine or fuel tank is far bigger than the room round a point; `src/lib/unit-3d/focus.ts`), clear of the part's callout point, inside the stage, off the callouts' labels and dots and the other flagged parts round their points wherever there's room clear of the part (a leader crossed rather than a dot covered; where none of the places it tries is free, the places against the edges of everything on the stage, which find one wherever there is one), as far as it can off the callouts' leaders, with a thin teal leader from its edge to that point (`src/lib/unit-3d/bubble.ts`; one point per system, so the leader marks the system's area); it stays where it is while that holds (to within a few pixels) as the camera turns or flies, only its leader following the part (placed on each frame the camera moves, straight on the element, nothing rendered again and nothing drawn while still), and the leader goes when the point leaves the stage; zoomed in so far that the part fills the stage, it goes against the stage's edge farthest from the part's middle, covering as little of it as it can. A tap on the drawing, or **Enlarge**, opens its page full screen zoomed to it (`:box-…`, as from the sheet; Back returns to the bubble); × puts it away until another part is picked or the part's chip is tapped again. Nothing shows while the part's sheet comes; once it has pages to look on, a still, empty frame (with its ×) until the first drawing is found, when one is sure to come (an exploded view among the pages) or the looking takes more than 0.4 seconds (a part whose pages have nothing to crop doesn't flash one); a part with no drawing gets no bubble; while another part's sheet comes, the last part's bubble stays, dimmed. Floating, it's a third of the stage wide, 220 to 440px. On a phone (a stage narrower than 560px or shorter than 360px) it's a strip docked across the top of the stage ("Starter motor · Exploded view · p.9") once it has a drawing or one is sure to come, the callouts laid out under it (while a drawing may yet come to nothing, the line under the stage says "Finding the drawing…" instead: a strip would hide the callouts' top row and take its taps, or drop it and bring it back) and the leader running down to the part when there's room, at a slant past the part's own callout label when that's in the way (none when it can't pass). Its controls are 44px. The line drawing (no WebGL) has no bubble; its sheet has the drawings as above.

- **Parts.** A reviewed list of what Polaris's manuals call the common parts of each system (`PART_NAMES` in `src/lib/diagnose-parts.ts`: starter solenoid, starter motor, battery, stator, regulator/rectifier… for charging/starting; spark plug, ignition coil, crankshaft position sensor… for ignition; with the parts only some machines have, like a recoil starter or a carburetor, kept to them), after the parts the conversation's causes in that system name ("Starter solenoid failing" is the starter solenoid, "Water in the speedometer connector" the speedometer connector, "Failed fuel pump relay" the fuel pump relay; "Air pocket in the cooling system" names none), the confirmed cause's first.
- **Pages.** The pages the causes naming the part cite (and their steps') come first. Then a full-text search of the conversation's manuals (its scope, else the unit's manuals by model number) for the part's name, ranked toward pages about the part, a heading in capitals naming it (its diagram or where it is: CARGO BOX, BATTERY LOCATION), its service procedure most (a heading like STARTER SOLENOID REPLACEMENT, procedure words such as SERVICE, REMOVAL, INSTALLATION and TORQUE, numbered steps, a torque spec, which only count on a page about the part), over pages that only mention it (a wiring diagram, a troubleshooting chart, another part's procedure that names it in a step), toward the unit's own manual, and a contents page last (after even a page with only some of the part's words; shown large only when the search finds nothing else, and then as a page that only names the part, with no card); the system's other causes' pages with the part on them get a little more. The best page is shown large and up to three more as small pictures. With no manual to search (no unit, or none of its manuals in the library) the sheet says so, with the cited pages only.
- **What the page says.** The first time anyone in the shop opens a page, Claude reads its text once (one plain request to a quick, cheap model, `PAGE_FACTS_MODEL` in `src/lib/manual-facts-rules.ts`, with no thinking and a strict `record_page_facts` tool it's told to call, since this model can't be forced to; asked once more if it answers without it) and records two things: the procedure's heading and the part number of each special tool it names ("PU-50638"); the tool has no place for anything else, and the prompt says the technician reads the steps, torque specs and cautions on the page itself. The card puts none of those in other words. Which torque value a PDF's text gives for which fastener can't be read for sure: a page in two columns comes out row by row across both, a text layer can give values before their labels, a table row wraps under its value, OCR misreads units, and a note or title can hand one fastener's value to another ("Cable fastener: as for the solenoid fastener"); a value beside the wrong fastener can strip a thread or let a part come loose. A step put in fewer words can read finished when it isn't ("Install the front wheel." for "Install the front wheel and tighten the wheel nuts to specification."), and a step or caution left out of a list leaves no mark that it was. The page itself is right beside the card. So whether the page has steps, torque specs or cautions is read from its own text, not asked of Claude (`readOnPage`): a line that starts like a numbered step ("1. Raise dump bed.", "5) Remove…"), torque information (`torqueOnPage`: the word TORQUE, as OCR may misread it too, spaced out or broken over a line; a torque unit in any spelling the rules read, "97 in-1bs", "97 in-Ihs", "11 N-rn", "11 Hm" and "35 in#" among them; or "to specification"), or a WARNING, CAUTION, NOTICE or DANGER anywhere on the page (as OCR may misread it: "WARNlNG", "CAUTl0N"). In doubt the line shows: it only costs a look at the page. What Claude records is then checked against the page's own text (`checkFacts`). The title is kept only if it's a heading the page prints, word for word (case and spaces aside), and says nothing of a torque: written with nothing but ASCII letters and digits and a sentence's marks (no "=", "→", ditto mark, quotes, possessive, spaced dash or colon, no letter or digit of another script); no torque unit, number in words, letters for digits or Roman numeral the page doesn't print; no word for torquing or tightening, or one that hands something on or compares ("same", "as", "per", "like", "see", "use", "both", "previous", "than" and more); no two fasteners or a pair of words said twice; and, on a page with torque information, no number or part number at all (elsewhere a number only in a unit that isn't a torque's, as the page prints it). A tool is kept by its part number: one the page prints exactly (dashes and case aside) shows as the page's own line with it, never Claude's words for it ("Use Digital Multimeter PU-50638.", from the first line with it that can be shown, a step's number at its start taken off), and a line that, its part numbers aside, has any other number (a figure, a callout, a digit of another script, a number in words), any torque information or a word for torquing or tightening, or is too long for the card, shows the part number alone, so nothing on it can pair a fastener with a value; a tool with no part number, or one the page doesn't print, isn't shown. A card needs a tool or the line: a title alone isn't one, and a page with neither (a wiring diagram, a contents page) has no card. The result is saved in `manual_page_facts` (row-level security and grants like the other per-shop tables, `drizzle/0026`–`0027`), also when the page has nothing for a card, so a page is never read again (`src/lib/manual-facts.ts`). A saved card is checked against the page again whenever it's shown, so one saved in an earlier shape (with steps, cautions, a torque list or notes) shows only what these rules allow, its tools as the page prints them, with no migration. Two devices opening the same page at once read it once: the page's row is claimed with one upsert, and the other is told it's being read. Without `ANTHROPIC_API_KEY`, past the shop's daily readings, or when a read fails, the page still shows without its card; a failed read is tried again after 15 minutes, not on every open. A failure that isn't the page's (the API busy or rate-limited, billing, also when the API says so with a 400 about the credit balance, the key or setup, a timeout or a dropped connection) doesn't count toward the page's three reads in all, so the card comes back once the service does. The rest count: a request the API turned down or found too long, no tool call even after asking again, and anything unrecognised (an error of the app's own, a status the API doesn't usually send), so a failure that would go the same way every time stops being paid for; a page Claude declined or ran out of room on isn't read again at all. A read whose server went away is taken over after 3 minutes (longer than the route may run), and counts as one of the three. A page with hardly any text (a scanned page OCR hasn't read, a diagram) isn't read.

### The drawing

Where the 3D unit can't run (no WebGL, an old browser, a lost context), and while it loads, the unit is an isometric-style line drawing, hand-built as inline SVG from code, in the same calm style on the same light plate: neutral grey line-work with faint face shading, see-through so the parts inside show in their real places, a soft ground shadow, no grid. There are three drawings: a side-by-side (RZR, Ranger, General, Xpedition), an ATV (Sportsman, Scrambler) and an open-frame generator; other units get no drawing and the panel works the same without it. Which one comes from the conversation's unit (`vehicle`, from the same `specForUnit`: the line's kind of vehicle, or else the brand codes and words as `vehicleForUnit` and `chooseVehicle` in `src/lib/unit-vehicle.ts` read them).

Claude tags each likely cause with one of 18 systems (`CAUSE_SYSTEMS` in `src/lib/diagnose-zones.ts`): engine, fuel, air intake, ignition, exhaust, cooling, charging/starting (battery, stator, regulator, starter), electrical (harness, ECU, sensors, switches, gauges, lights), drive clutch (CVT belt and clutches), transmission, front drive (front gearcase, AWD, prop shaft, front axles), rear drive (rear gearcase and axles), brakes, steering (including EPS), suspension, wheels/tires, body/frame, or other. It's a required enum on each cause in the strict `submit_diagnosis` schema. The tools stream their input (`eager_input_streaming`), and then the API doesn't hold Claude to the schema, so the reply check takes the system when it's on the list (case and spaces aside) and otherwise works it out from the cause's words, like an older reply's; other only when nothing matches. Every system but other is its own region of the side-by-side and ATV drawings; the generator has the ten that apply. Replies saved before causes carried a system get one from the cause's words (`inferSystem`: coil, plug or spark → ignition; injector or fuel pump → fuel; belt or clutch → drive clutch; stator, regulator, battery or starter → charging/starting; and so on), so older conversations light up too. Every rule that matches is scored by the length of the words it matched and the longest wins, so a specific part beats a generic word: "spark arrestor" is exhaust, not ignition's "spark"; "AWD coil" or "front gearcase coil" is front drive, not an ignition coil; "Hilliard clutch" front drive; "engine braking" (EBS) drive clutch; "throttle return spring" air intake; a "… sensor" electrical; "gas cap vent" fuel. Changing the list changes `submit_diagnosis`, with the same effect on open conversations as editing a tool description (see Model and settings).

How a system is drawn comes from its causes, with the 3D unit's colours: confirmed → filled deep red with a dark outline and a check badge on its callout; open and high → filled deep red; open and medium → filled amber; open and low → only a red outline; only ruled-out causes → grey, with a small grey cross where it is; none → plain line-work. Nothing glows, pulses or is blurred (the styles have no filters or animation). Once a cause is confirmed the other open systems are toned down to pale tints, so the confirmed part stands out. Flagged systems get numbered callouts (the circle carries the cause's number in the list, the name and the same three-bar likelihood meter beside it) in a band above the drawing and one below, a thin leader from a dot on the part to the circle; ruled-out systems get the cross on the drawing but no callout. The likeliest get the row nearest the drawing, labels keep their parts' left-to-right order, a label crosses to the other band rather than start a second row, and no leader runs through another label: one in an outer row drops through a gap in the row inside it (or runs along the channel between rows). Leaders are drawn under the labels, and each label's tap target reaches half way to its neighbours, never over them. The key shows the callouts by number with their likelihood in words; causes whose system isn't drawn are listed under it. The drawing scales as a whole, so the server and the browser draw the same thing and nothing jumps after loading. It carries both sets of callouts and a container query picks one: the full labels (about 11–12px beside the chat, bigger on a portrait tablet), or, on a card under about 450px wide (a phone), the numbered circles alone, drawn nearly twice the labels' size (about 11px numbers) with the key under the drawing naming them. Tapping a label picks its system and highlights its causes in the list (scrolling them into view); a mouse hovering a cause, tapping a cause, or its system chip lights its system (a finger's tap doesn't count as hovering). Tapping a system's parts, lit or not, opens its sheet full screen on its own (there's no 3D unit to examine; `?examine=<system>` as in the examine view, closed by Back or Esc): a lit system is its own shape on the drawing, and the others, merged into the line-work, are found from the drawing itself, each system's paths tested in a 2D canvas (faces by their fill, lines and tubes a few pixels either side), small parts first, so nothing is added to the markup. The drawing is a `role="img"` group whose label names the lit systems; each lit system is a focusable button (Enter or Space opens its sheet).

The geometry is pure and tested (`src/lib/unit-graphic/`): `iso.ts` is a small 3D kit (a fixed parallel camera; boxes, lofts, extruded profiles, cylinders, tubes, springs) that writes compact SVG path data; `utv.ts`, `atv.ts` and `generator.ts` place the parts in centimetres, each tagged with its system; `drawing.ts` paints them in layers (far wheels, body shell, insides, cage, near wheels) and keeps each system's paths and label point; `callouts.ts` lays out the labels; `scene.ts` puts together what the component draws for a set of lit systems; `style.ts` holds the styles. A flagged system is drawn once, over line-work it has been left out of, so flagging systems adds little: each drawing is about 30 KB of SVG unlit (the generator 13 KB), and under 40 KB with five or six systems flagged and called out. The client component is `src/app/(app)/diagnose/unit-graphic.tsx`.

### History, caching and context

- **Append-only history.** Each message's exact API messages (the tech's text, any app note, then Claude's responses with their thinking, tool calls and web search blocks exactly as they came back, and the tool results) are stored in `diagnosis_turns.history` as `json` (not `jsonb`, which would reorder keys), and every later request sends all earlier finished messages unchanged before the new one. Nothing is edited or dropped: Claude's thinking blocks are tied to the exact conversation that produced them, and prompt caching is a prefix match. Failed and stopped messages aren't kept in the history, so a retry sends the same text again after the last finished message. App notes (the unit the tech picked or changed, their Ruled out / This was it presses, their ticks on checks) go in as mid-conversation `system` messages, which the tech's own text can't imitate. Turning web search off later doesn't change a conversation's tool list: it appends a `tool_removal` message (beta `mid-conversation-tool-changes-2026-07-01`).
- **Prompt caching.** The system prompt and tools are fixed (no dates, names or IDs) and come first, with a cache breakpoint at their end, plus top-level automatic caching for the growing conversation. Both use the 1-hour TTL: techs often reply after 10–30 minutes in the bay, past the 5-minute cache, and re-writing the whole conversation after every break costs more than the 1-hour write premium (2x input instead of 1.25x; reads are 0.05x).
- **Context growth.** Old tool results stay in the history rather than being cleared with context editing: with cache reads at $0.20 per million tokens, re-reading a 50,000-token conversation costs a cent per request, while clearing results would invalidate the cache from that point on every time it ran and take away pages Claude may cite again. Instead, each message is capped (below) and a conversation ends at 40 messages or once Claude's prompt passes 300,000 tokens (the prompt of the last sampling step in `usage.iterations`: the top-level counts add up every step of a server-side web search), with **Start a new diagnosis for this unit**, which carries the unit, manuals and current causes over, and the checks that were next with what the tech found on the ones ticked off ("(done: OK)").

### Model and settings

`DIAGNOSE_MODEL` in `src/lib/diagnose-rules.ts` is the only place the model is named (`claude-opus-5-5`; its prices are next to it, with `claude-sonnet-5-5`'s for comparison and those of the models a refusal fallback can hand a message to). Requests (`buildRequest` in `src/lib/diagnose-prompt.ts`) use adaptive thinking (the only kind on this model) at effort `high`, set explicitly since the default is `medium`, no temperature/top_p/top_k and no prefill, `max_tokens` 32,000 (thinking counts toward it; a response cut off there is asked for again once with 64,000). Server-side refusal fallbacks are on: `fallbacks: "default"` with beta `server-side-fallback-2026-07-01`, so a safety-classifier decline is re-run on Anthropic's recommended model in the same call (`DIAGNOSE_REFUSAL_FALLBACK=off` turns it off). The loop checks `stop_reason` before reading anything: `refusal` (the whole chain declined) and `model_context_window_exceeded` end the message with a plain explanation, `max_tokens` is retried as above, and `pause_turn` (a long web search) is sent back as it was so it carries on. API errors use the SDK's typed errors (it retries 429s and 5xx twice first), and an error sent part way through a stream, which the SDK can't retry, is sorted by its type: an overload there is retried once after two seconds; rate limits and overloads say to wait a minute, a bad key says to check `ANTHROPIC_API_KEY`, and a billing error (402, or a 400 saying the credit balance is too low) says to check the plan and credits in the Claude Console.

Claude's thinking blocks are tied to everything before them in the conversation: the system prompt, the tools and every earlier message. Every request sets `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` with its beta header `thinking-binding-controls-2026-08-01` (the field is a 400 without the header, so they always go together). The history never changes, so nothing is dropped in normal use, but **editing `SYSTEM_PROMPT`, a tool's description or a limit written into them (`DIAGNOSE_LIMITS.pageTextCharacters`, `searchHits`, `webSearches`) changes the start of every open conversation**: with `drop_block` the API leaves out their earlier reasoning and carries on, instead of failing every message in them (on accounts created since 31 August 2026 that's a 400, and Retry would repeat it), and their prompt cache starts over. Each drop is logged as a warning (`Diagnose: earlier thinking didn't match the conversation`); drops after a refusal fallback to another model are expected and not logged.

### Limits

- Per tech message: 12 requests to Claude, 30 page reads, 60 manual searches, 6 unit lookups (all three enforced in code), and a budget of 5 web searches (enforced by the API per request; across the message, Claude is told to stop after 5, see above). Past a limit the tool result tells Claude to answer with what it has; the last step tells it to wrap up. A message that still hasn't answered shows Claude's text, if any, with the previous reply's causes. Each message also has the time limit above.
- Per conversation: 40 messages, or a prompt over 300,000 tokens.
- Rate limits, counted in `attempt_counters` per message (retries too): 30 per tech per hour, 500 per shop per day, with a message saying when they can send again.
- Page readings for the part sheet: 300 per shop per day, counted in `attempt_counters` (a page is only ever read once, so this only matters on a shop's first busy days).
- Managers and admins see this month's conversations, messages, web searches and solved count on the Diagnose tab.

### Cost

Kept for the records, not shown in the app. Estimated per message from the API's token counts at Claude Opus 5.5's list prices: $4 per million input tokens, $20 output, cache reads $0.20, cache writes 1.25x input (5-minute) or 2x (1-hour); web search at $10 per 1,000 searches (Anthropic's list price; it isn't in the API reference this was built from, so `WEB_SEARCH_DOLLARS_PER_1000` is marked to check). Each response is priced from `usage.iterations` when the API sends it, step by step at the rates of the model that ran each step: after a refusal fallback the declined attempt counts too, and the fallback model's part is priced as that model (Claude Opus 5 or Opus 4.8, $5 / $25). A request cut off part way (Stop, the time limit, an error in the stream) still counts the prompt it had reported, and a retried message adds every attempt's cost, so the recorded per-message and monthly figures include failed attempts. Output tokens dominate: at effort `high` Claude thinks before each tool call, and thinking is billed as output. The fixed part of every request (system prompt and tools) is about 3,200 tokens and is read from the cache for a fraction of a cent. A first message typically takes 4–6 requests (unit lookup, a couple of searches, a page read or two, a web search, the answer), roughly 10,000 output tokens and 25,000 tokens written to the cache: about 40–50¢. A follow-up with a search and a page read takes about 3 requests: about 20–30¢. A five-message diagnosis comes to roughly $1–1.50, about a third of what it would cost without prompt caching. The recorded figures (each message's in `diagnosis_turns.cost_cents`, the month's on the Diagnose tab) are worked out from the API's actual token counts, so check those against this after the first real week. (The end-to-end run's stand-in API, with short test pages and token counts estimated from request sizes, gave 14¢ for five messages with caching and 37¢ without; real pages, web results and thinking are several times bigger.) A page reading for the part sheet is about 1,500 tokens in and a few hundred out at the reading model's prices: about a cent, once per page, kept in `manual_page_facts.cost_cents`.

### Setup

Add `ANTHROPIC_API_KEY` (from the Claude Console) in Vercel → Settings → Environment Variables for **Production** and **Preview**, then redeploy. Until it's set the Diagnose tab says it isn't set up, and nothing calls the API. `ANTHROPIC_BASE_URL` only points tests at a stand-in API; leave it unset. Optional: `DIAGNOSE_WEB_SEARCH=off`, `DIAGNOSE_REFUSAL_FALLBACK=off`.

### Privacy

The tech's messages (with the unit's VIN when they give one), the text of the manual pages Claude searches and reads, and the web search queries go to Anthropic's API; web search reaches the public web, and Claude may search it with the VIN (for recalls, say). The part sheet sends a manual page's text once, the first time the page is opened. Nothing else about the shop (names, accounts, customers) is sent: a customer's vehicle picked on New diagnosis only fills in the quick form's model number and VIN, which the tech sees and can change, and the customer's name and contact details never leave the app. Conversations are shop records: `diagnosis_conversations` and `diagnosis_turns` have a `shop_id`, row-level security, and grants that let `app_user` add and update them, and delete a whole conversation (see Deleting a diagnosis), but never delete a message on its own or change who sent what (`drizzle/0019_diagnosis_grants.sql`, `drizzle/0037_diagnosis_delete_grants.sql`).

### Deleting a diagnosis

Managers and admins (`diagnostics.delete`, signed in with a password, so never from a bay tablet's PIN session) get **Delete diagnosis** under a conversation (`src/app/(app)/diagnose/delete-diagnosis.tsx`), for one started by mistake, a test or a duplicate. It asks first, with an optional box for why (up to 200 characters), and goes back to the list, which says what was deleted and links to the Activity log; Back doesn't return to it. `deleteConversation` in `src/lib/diagnose.ts` deletes the conversation and its messages for good and, in the same transaction, writes `diagnosis.deleted` to the Activity log with what it was: its title, unit, model number and VIN, Open or Solved (and the fix), who started it and when, when it was last used, its messages and cost, the customer and vehicle it was linked to, and the reason. That entry can't be changed or deleted, like every entry in the log. It's refused while Claude is answering one of its messages (stop it, or wait); a message whose server went quiet doesn't hold it up. A deleted diagnosis no longer counts in the Diagnose tab's figures for the month or on Home, and its customer's vehicle can then be removed if that was a mistake too.
